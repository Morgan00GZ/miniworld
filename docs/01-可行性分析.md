# 01 · 可行性分析（澎湃 OS 4 / HyperOS）

> 本文的结论是**可以做出真同屏多窗口工作台，但不是所有手机、所有 App 都能**。
> 所有"能不能"的答案都必须由 `tools/probe-hyperos.ps1` 与 App 内「一键自检」在真机上给出。
> 本文负责说清楚：机制是什么、哪一步可能断、断了怎么办。

> **修订提示（2026-10，真机实测后）**：**本文第 1 节的"可行性"判断已被真机实测证实**。
> 之前的版本曾据一份**有 bug 的探测脚本**得出"自建自由窗口走不通、只能退到档位 B/C"的结论——
> 那是**误判**。脚本的三处 bug 修复后，在 Xiaomi 25098PN5AC（澎湃 OS 4.0 / Android 17）上重跑，
> 遥控实测 **PASS=19 WARN=4 FAIL=0**：自由窗口起得来、尺寸改得动、任务前置得了，
> **档位 A（系统自由窗口真同屏平铺）成立**。踩坑记录见第 7 节。
>
> 虚拟屏（档位 D）**仍是可选增强**，但它不能再用 `overlay_display_devices` 走捷径（实测被
> `SecurityException` 拒，见 P18.3）；必须先做「App 自建 VirtualDisplay」PoC（M2-2）。
> 档位优先级以 [docs/05](05-需求收敛与架构定稿.md) 的档位表为准。

## 1. 结论先行

下表已按 Xiaomi 25098PN5AC（澎湃 OS 4.0 / Android 17）的**真机实测结果**填写。
"实测"一列写的是探测编号，逐条证据见第 3 节与 [docs/03](03-真机验证清单.md) 的「真实设备验证结果」。

| 目标 | 可行性 | 依赖 | 实测 |
| --- | --- | --- | --- |
| 多个**不同** App 同时显示在屏幕上 | **高（实测成立）** | 系统 Freeform（`windowingMode=5`） | P2 PASS：taskId=91、`mode=freeform` |
| 这些 App 同时保持运行（不暂停） | 高 | Android 10+ **multi-resume**：可见窗口即 `RESUMED` | P6 待人眼确认；机制见 2.3 |
| 任意窗口改位置 / 改大小（栅格编排） | **高（实测成立）** | `am task resize <taskId> <L> <T> <R> <B>`（4 个分开的数字） | P3 PASS：`mBounds=Rect(0,0-540,1200)` |
| 一键把某个 App 换到主位 | **高（实测成立）** | `am task focus`（实测可用）/ 回退 `--activity-reorder-to-front` | P4 PASS：输出 `Setting focus to task 91` |
| 后台不被冻结（挂机保活） | 高 | `cmd deviceidle whitelist` / `am set-standby-bucket` / `cmd appops` | P7 PASS：`bucket=10(active)`、`freezer=disabled` |
| 多个自由窗口**共存**（≥2 个） | 待验证 | ROM 是否允许同时存在 2 个 freeform 任务 | P5 未测（第二应用未安装） |
| **同一个游戏开多个号**同时跑 | **低（不在本方案内）** | 需要应用分身 / 多用户沙箱，属于另一个问题 | — |
| 4 个全尺寸游戏同时满帧 | **低（物理限制）** | CPU/GPU/内存/散热，与软件无关 | — |

**关键洞察**：Android 的"后台 App 被暂停"并不是因为它在后台，而是因为它的窗口不可见。
Freeform 把窗口留在屏幕上，就同时解决了"切换要重新加载"和"挂机会掉线"两个问题。
这正是锤子「一步」和 OriginOS「原子工作台」的底层原理，也是小米官方文档里
"迷你小窗用于应用临时挂机"那一句的技术含义。

### 1.1 为什么 A 档能同时"挂机"和"看视频"

这正是实测 P2+P3+P4 三项全过之后才敢下的结论，逻辑链只有三步：

1. **同屏 = 都可见**：两个自由窗口在同一块屏幕上各占一块矩形，谁也没盖住谁。
2. **都可见 = 都 `RESUMED`**：Android 10+ 的 multi-resume 规定，多窗口设备上"可见的
   Activity 可以同时处于 `RESUMED`"，而不是传统的"只有一个前台、其余 `PAUSED`"。
3. **`RESUMED` = 都继续跑**：游戏继续渲染推逻辑、视频继续解码播放。

所以"挂机"和"看视频"**不是二选一**：它们是屏幕上的两张并列的窗口。
这也解释了"一键前置"为什么不能退化成"重新 launch"——前置只是改变焦点与层级，
窗口一直活着，进度和登录态原地保留（见 [docs/02](02-架构与命令映射.md) 3.4）。

**边界要说清**：焦点仍然只有一个。失焦窗口会收到 `onWindowFocusChanged(false)`，
**应用可以据此自觉暂停**——这是应用侧行为，系统无法强制（见风险 R1）。
所以 P6（失焦窗口是否继续运行）仍需人眼确认，且建议"游戏做主位、视频做小窗"。

## 2. 系统机制

### 2.1 小米小窗 = Android Freeform

小米澎湃 OS 开发者文档《全局自由窗口适配说明》原文：

> MIUI 的小窗是基于 Android 的多窗口 Freeform 方案实现的。

这条官方说明意味着：**Freeform 这条系统通路在小米设备上是存在且被使用的**，
不是"原生有、小米砍掉了"。差别在于 MIUI/HyperOS 在自己的窗口管理层（小窗、迷你小窗、
贴边小窗）之上加了一套交互策略与限制，而 AOSP 的 Freeform 入口（`windowingMode=5`）
默认不对外开放。我们要做的是绕过"交互策略"，直接用 AMS 的通路。

### 2.2 开关：`enable_freeform_support`

AOSP 中 `ActivityTaskManagerService` 在**开机时**读取一次：

```
Settings.Global.ENABLE_FREEFORM_SUPPORT
  或 PackageManager.FEATURE_FREEFORM_WINDOW_MANAGEMENT
→ mSupportsFreeformWindowManagement
```

两个推论：

1. `settings put global enable_freeform_support 1` **通常需要重启一次**才生效。
   所以 App 不会静默改写它，而是"检测到 0 就提示用户改 + 重启"。
2. 如果小米把 `FEATURE_FREEFORM_WINDOW_MANAGEMENT` 特性标记打上了（很可能，因为小窗依赖 Freeform），
   那么**根本不需要这个开关**，改完即用。

> **实测（P1）**：本机 `enable_freeform_support=0`、`force_resizable_activities=1`、
> `FEATURE_FREEFORM_WINDOW_MANAGEMENT=True`。
> 即：**第 2 个推论在本机成立**——开关是 0 并不代表不能用，系统特性已声明 Freeform 可用，
> **无需改设置、无需重启**，自由窗口本来就可用（随后的 P2/P3/P4 三次 PASS 是直接证据）。
> 这与旧文档"必须改开关并重启"的预期正好相反，是本次实测修正的一处结论。

### 2.3 multi-resume：为什么"同屏"就等于"同时运行"

Android 10 起，支持多窗口的设备上，**多个可见 Activity 可以同时处于 `RESUMED`**。
Android 官方说明见 *Multi-resume*。落到实践：

- 全屏 A + 后台 B → B 是 `PAUSED`/`STOPPED`，游戏停、视频停。
- 同屏 A + B（都可见） → 两者都 `RESUMED`，游戏继续跑、视频继续播。
- 焦点只有一个，但**焦点≠运行状态**。失焦的窗口仍会收到 `onWindowFocusChanged(false)`，
  应用可以据此自觉暂停——这是应用侧行为，系统无法强制（见风险 R1）。

### 2.4 Shizuku 的位置

Shizuku 通过 ADB / 无线调试启动一个进程，让普通 App 能以 **shell（uid 2000）** 身份执行代码与命令。
它给的是**权限借用**，不是 Hook。因此：

- 能做：`am` / `settings` / `cmd` / `appops` 等特权命令、以 shell 身份启动指定窗口模式的 Activity。
- 不能做：改别的进程行为、拦截全局输入、给别人的 Service 注入 Binder。

所以凡是要"让某个 App 不要自己暂停"的需求，**没有任何免 root 手段能做到**，
只能选那些不会自己暂停的 App，或用"可见即 resumed"绕过。

## 4. 风险清单

| 编号 | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 目标游戏在失焦时主动停止绘制/暂停 | 主位以外的游戏面面黑屏或掉线 | 无法系统级解决；自检页明确提示；建议场景里"游戏做主位、视频做小窗" |

| R5 | 功耗/发热导致降频、掉帧 | 多游戏场景体验差 | 场景建议上限"1 主 + 2 迷你"；不做 4 个全尺寸 |

| R8 | ROM 差异导致命令失效 | 静默失败 | 每条命令都有"执行→按输出判定成功/失败"，失败进日志并在自检页标红 |

## 5. 明确不做的事

- **不做应用多开**：同一 App 的多个实例需要分身/多用户/沙箱（如 VMOS、Island），
  与本方案的"多窗口编排"是两条完全不同的路，混在一起会让架构失控。
- **不做 Hook / Xposed / 内核模块**：那需要 root 或 LSPosed，与"只用 Shizuku"的定位冲突。
- **不做录屏式"伪小窗"**（把后台 App 的截图贴到浮窗上）：画面不实时、不能操作，是假的多开。
- **不做全局触摸拦截**：会破坏系统手势（返回、下拉状态栏），代价大于收益。

## 6. 与同类方案的差异

| 方案 | 机制 | 局限 |
| --- | --- | --- |
| 小米原生小窗/迷你小窗 | 系统自带 | 一次只能手动开一个，无编排、无场景、无批量保活 |

## 7. 踩坑记录：一次由探测脚本 bug 导致的误判

**这是本项目最重要的一条教训。** 上一版探测脚本有三个 bug，它们叠加在一起，
把一台**完全支持自由窗口**的机器判成了"走不通"，进而让文档写下了"只能退到档位 B/C"的错误结论。
三处 bug 已全部修复，重跑后 `PASS=19 WARN=4 FAIL=0`。

### 7.1 `am task resize` 的 bounds 不能写成单个逗号串（**误判主因**）

```bash
# ✗ 错误写法（上一版就是这么写的）
am task resize 91 0,0,540,1200
#   → java.lang.NumberFormatException: For input string: "0,0,540,1200"
#     （ActivityManagerShellCommand.getBounds / runTaskResize）

# ✓ 正确写法：4 个分开的数字
am task resize 91 0 0 540 1200
```

后果：P0.3「`am task resize` 可用」被判 FAIL、P3 的实测被判 FAIL，
于是"能起窗口但不能改尺寸"→ 栅格编排不成立 → 退档位 B/C。

### 7.2 `displayId` 解析：整块匹配 + 大小写不敏感 + `[int]` 强转

```powershell
# ✗ 上一版：整块匹配 DisplayDeviceInfo{...}
#   问题 1：该行极长且含嵌套花括号，会截断；
#   问题 2：PowerShell 的 -match 默认忽略大小写，会把
#           mDisplayId=4630946949513469331（19 位 display token 长整型）也命中；
#   问题 3：[int] 强转 → Cannot convert value "4630946949513469331" to type "System.Int32"
#   这是「终止性」异常：P18 的 try 块直接跳到 finally，
#   导致 P18.2 / P18.3 静默消失，只剩 P18.1 和 P18.5。

# ✓ 修法：区分大小写 + 限定 1–3 位数字 + TryParse 兜底
if ($line -cmatch '\bdisplayId[ =]+(\d{1,3})\b') {
    if ([int]::TryParse($Matches[1], [ref]$n)) { $ids += $n }
}
```

> 存档对照：旧的 `tools/probe-output/probe-result.json` 里 P18.1 的 detail 是「现有 displayId: **解析失败**」、
> P18.2 是「没有出现新的 displayId」——这正是 7.2 的症状。修好后 P18.2 立刻报出新增 `displayId=7`。

### 7.3 `am help` 匹配子命令的方式（假阴性）

`am help | Select-String 'resize'` 是**假阴性**匹配：`am help` 里子命令是缩进罗列的，
`resize` 的用法行缩进特殊，根本不会出现 `task resize` 这种带父命令的写法。
正确做法是**按行首格式判断子命令是否存在**：

```powershell
$hasResizeTask = $amHelp -match '(?m)^\s*resize\s*<TASK_ID>'
```

### 7.4 教训（写给下一个改动脚本的人）

1. **"命令不存在"和"命令写错了"必须能区分开**。前者是能力缺失，后者是脚本 bug，
   但两者在探测输出里都表现为非零/报错。判 FAIL 之前先看原始输出。
2. **PowerShell 的终止性异常会静默吞掉后续探测项**。任何解析都要 `TryParse` + 兜底，
   避免"一个解析错误导致一整段实验凭空消失"。
3. **数值解析一律限定形状**（大小写敏感 + 数字位数），别依赖"整块匹配 + 类型转换"。
4. **结论只看关键能力项（P2 / P3 / P4）**，不看 FAIL 个数——这一点已固化进脚本收尾逻辑。
