## 1. 一句话目标与验收标准

**一句话**：让一个（横屏）手游在后台**隐形保活**——画面看不见，但进程活着、不掉线、不卡顿；想用时点一下悬浮图标就浮出来操作，再点一下收回去，点"关闭"能干净地结束它。

**做完的标准（Definition of Done）**：

| # | 能力 | 怎么算通过 |
|---|---|---|
| 1 | 隐形保活 | 点"启动"后目标应用缩成右下角 2×2 像素；挂 10 分钟不掉线、单机游戏不卡住（进程仍在 `pidof` 里、窗口 `visible=true`） |
| 2 | 一键浮出 | 点 Dock 图标 → 浮窗出现（可用区 3/4 宽、16:9、居中），**可正常操作**（触控映射对、按钮在） |
| 3 | 一键收回 | 再点一下 → 回到 2×2，屏幕上看不见 |
| 4 | 不变形 | 打开主页/微信再回桌面，屏幕上**不会**冒出变形窗口（这是最容易翻车的一条） |
| 5 | 关得掉 | 点"关闭"→ 进程结束，且"最近任务"里那张卡片也没了 |
| 6 | 能换应用 | 界面里能从**已安装应用列表**里换挂机对象，包含手机分身里的那一份（userId 999） |
| 7 | 界面够简单 | 一页：启动 / 关闭 / 更换 / 状态 / 三行权限；不需要用户理解任何技术名词 |

## 3. 开工前的能力预检（先验证，再设计）

换机型第一件事：把下面这些命令跑一遍，把结果记下来。**不要假设**。

| 要验证的能力 | 命令（经 Shizuku 或 adb shell 跑） | 期望 / 说明 |
|---|---|---|
| 特权通道 | `id` | `uid=2000(shell)` |
| 读窗口状态 | `dumpsys activity activities` | 能看到任务块：`Task{... #787 type=standard A=1000:com.xxx}` 与 `mBounds=Rect(...)` |
| 自由窗口可用性 | `settings get global enable_freeform_support` / `pm list features \| grep freeform` | `1` 或特性里有 `android.software.freeform_window_management` |
| 能不能起自由窗口 | `am start --user 0 -n <包>/<Activity> --windowingMode 5` | 任务出现且 `mode=freeform` |
| 能不能摆位 | `am task resize <taskId> <l> <t> <r> <b>` | **四个空格分隔的数字**；逗号串会抛 `NumberFormatException` |
| 能不能前置任务 | `am task focus <taskId>` | 输出 `Setting focus to task N`；注意 `am help` **不列**这条，但实测可用 |
| 能不能清最近任务 | `am stack remove <taskId>` | `am task remove` **不存在**（`Error: unknown command 'remove'`） |
| 谁拿着焦点 | 在 `dumpsys activity activities` 里找 `topDisplayFocusedRootTask=` 与 `topResumedActivity=` | 后者尾部的 `t<数字>` = 用户此刻在看的任务 |
| 分身列表 | `pm list users` | 分身会显示成 `UserInfo{999:...}` |

> 结论先行：这台机器 `am start --bounds` **不支持**（抛 `NumberFormatException`），`settings put system user_rotation` / `wm user-rotation lock` **锁不了屏幕方向**，shell **没有** `CREATE_VIRTUAL_DISPLAY` 权限。这三条决定了整条技术路线不能往"虚拟屏 / 锁方向 / 一步摆位"上走。

## 4. 技术路线（30 秒版）

```
Shizuku(shell, uid 2000)
   └─ am start --windowingMode 5   ← 把目标应用起成「自由窗口」
        └─ am task resize … 2 2   ← 缩到右下角 2×2 像素
             └─ 窗口仍然「可见」 → 进程保持 RESUMED、画面继续渲染、网络不断
                  └─ 悬浮 Dock（SYSTEM_ALERT_WINDOW）点一下
                       ├─ 浮出：两步 resize 到「可用区 3/4 宽、16:9、居中」+ am task focus
                       └─ 收回：resize 回 2×2
   └─ 每 2 秒看门狗：把跑偏的窗口拉回目标矩形；若焦点被系统抢走 → am task focus 还给用户
   └─ 关闭：am force-stop [--user N] <包名> + am stack remove <启动前取到的 taskId>
```

**为什么必须是"可见的 2×2"**：Android 的 multi-resume 判定是"**窗口可见就 RESUMED**"。把应用挪到屏幕外、或用纯后台方式保活，进程会被系统冻结（实测：单机游戏卡住、网络会话掉线）。缩成 2×2 像素仍然算"在屏幕上"，视觉占用为 0，但状态保住了。

**不要走的三条路**（都实测过）：

1. **平铺多个窗口**：小窗会压在主窗上、主窗不放大、背后发黑；用户直接否决，且这台 ROM 不支持 `--bounds`。
2. **纯后台保活**（不占窗口）：进程被 PAUSED，游戏卡住、会话掉线。
3. **虚拟显示 / 副屏 / 画中画**：副屏 `state OFF` 且是 presentation 类型；虚拟屏需要 shell 没有的权限；PIP 是缩略窗、操作受限。

## 7. 必须抄对的 12 个关键点

> 每条都是"错了就白干"的级别。格式：**正确写法** / 错误写法 / 后果。

1. **Shizuku 取进程**：反射调用隐藏方法 `Shizuku.newProcess(String[], String[], String)`（找不到就降级提示，不要崩）。
   直接调用公开 API 拿不到这条通道；反射失败时要在首页那行状态里说清楚"未授权或 API 变了"。
2. **取命令结果**：自己**轮询 `exitValue()`** —— 不能直接用 `process.waitFor(timeout, unit)`。
   `ShizukuRemoteProcess` 继承的默认 `waitFor` 只捕获 `IllegalThreadStateException`，在这台 ROM 上会把 Binder 异常变形后抛出来。两种异常都要当成"还没结束"。
3. **正则一律包一层 `rx()`**：`runCatching { Regex(p) }.getOrElse { NEVER_MATCH }`。
   裸 `Regex(...)` 在真机 ICU 上会抛 `PatternSyntaxException` **直接闪退**（本项目就栽过一次：任务头正则结尾的 `}` 没转义），而 JVM 单测测不出来。
4. **`am task resize` 的参数是四个空格分隔的数字**：`am task resize 787 100 200 900 1400`。
   逗号串（`100,200,900,1400`）必抛 `NumberFormatException`。
5. **不要用 `am start --bounds`**：本机不支持。用 `--windowingMode 5` 起自由窗口，随后 `am task resize` 摆位。
6. **清"最近任务"卡片要用 `am stack remove <taskId>`**：`am task remove` **不存在**。
   而且 **taskId 必须在 `am force-stop` 之前取**——force-stop 之后任务就从活动列表里消失了，取不到 id。
7. **启动一律显式带用户号**：`am start --user 999 -n <包>/<Activity> --windowingMode 5`，组件串也可写成 `<包>/<Activity>@999`。
   不写 `--user` 时，装有分身的应用会弹"选哪一个"的系统选择框，表现是启动失败、窗口乱跳。
8. **两步摆位**：`resize(缩到目标的 3/5)` → `sleep(350ms)` → `resize(目标)`。
   单次 resize 在这台 ROM 上"返回成功但不生效"，尤其在转屏之后（真机现象：收起状态转一下屏，浮窗又自己弹出来）。
9. **resize 之后必须复查**：`sleep(250ms)` 再读一次 `mBounds`，和期望值比（容差 24px）。
   只看退出码会被 ROM 骗过去；读不到 bounds 时要如实记录"按退出码判断"，不要假装验证过了。
10. **焦点交还只发一条 `am task focus`**：把焦点还给"显示级 `topResumedActivity` 的 `t<id>`"。
    这条 `topResumedActivity` 在 dump 里出现多次，**显示级那条在最后**，所以取**最后一个**匹配；另加 3 秒冷却。浮出态不介入、横屏不介入。
11. **单槽必须特判成"隐形小点"**：只有一个应用时，目标矩形 = 右下角 2×2，而不是布局算出来的"整块可用区"。
    不特判的话看门狗每 2 秒就把它放大弹出一次（真机现象：收起来两三秒后自动弹出、无限循环）。
12. **看门狗要放过"用户手动浮出的那个"**：记住 `manualOverlay` 包名，校正和置顶都跳过它，否则用户浮出 6 秒后就被掰回小点。
    同理，看门狗里"重新置顶"要针对**当前应该在前的那个**（按窗口顺序），不是固定第一个。

**附带两条环境事实**：
- `am task focus` 在 `am help` 里**不列**，但实测可用；判定能力时要用三态（"没列"≠"不支持"），最终以实测为准。
- `ScreenMetrics` 取的是**自然方向**尺寸（竖屏的 1220×2656）。横屏时必须把长边当宽用，否则浮窗又窄又长（真机反馈过）。

## 8. 真机陷阱清单（现象 → 原因 → 处理）

| 现象 | 原因 | 处理 |
|---|---|---|
| 浮窗"自己弹出来 + 变形 + 收不回" | 受管的 2×2 窗口被系统顶成 `topDisplayFocusedRootTask`，系统给它画标题栏并重新显示内容 | 焦点交还（§7.10）。**注意此时任务矩形和窗口 `Requested w=2 h=2` 全都正常——比几何的判据都判不出来** |
| 收起来几秒后自动弹出、循环 | 单槽没特判成小点 / 看门狗没放过手动浮出的窗口 | §7.11、§7.12 |
| 浮窗里游戏画面错位、按钮丢失、触控失效 | ROM 没给浮窗派发一次配置变化 | 摆位分两步（§7.8）制造配置变化；实测"在浮窗可见时手动切一次横竖屏"也能恢复，但用 shell 锁方向是**无效**的 |
| 点 Dock 没反应 / 浮出来又是原样 | 旧 taskId 已失效（浮窗被全屏过、转过屏） | 每次操作都按"包名 + 用户号"重新查任务，不要缓存 taskId 复用 |
| 关闭后"最近任务"里还有卡片 | `am force-stop` 只结束进程，不动最近任务记录 | 加 `am stack remove`（§7.6） |
| 有分身的应用弹出"选哪一个" | 启动命令没带 `--user` | §7.7 |
| 悬浮图标条完全不出现 | 没有悬浮窗权限 | `adb shell appops set com.miniworld SYSTEM_ALERT_WINDOW allow` |
| Shizuku 显示未授权 | 重装/改包名后授权失效 | 手机上重新授权；首页三行权限里直接给结论 |
| `INSTALL_FAILED_USER_RESTRICTED` | MIUI 的 USB 安装限制 | 重试一次；仍失败就去开发者选项里确认"USB 安装" |
| 崩溃了但 `logcat` 什么都没有 | 本机 `logcat` 缓冲区常被抽干 | 用应用自落的 `diag.log`；再兜 `adb shell dumpsys dropbox --print` |
| 想自动化点按却总点不中 | 本机 `uiautomator dump` 是坏的 | 给应用留**调试启动参数**（`am start … --ez <key> true`）直接触发某条路径，别依赖点按（1.0 里没有这类参数，需要时再加回） |

## 9. 测试与调试

**能单测的**（纯 JVM，`isReturnDefaultValues = true`）：
- `LayoutEngine.layout()`：不变量——数量恒等于槽位数、矩形有效且在可用区内、主位面积不小于其他；另有形状用例（槽位 0 = 整个可用区、其余为右下角贴边的 2×2 小点）与非法可用区降级（`LayoutEngineTest`，5 例）。
  **不要写"两两不重叠"**：小点按设计就压在槽位 0 的右下角上，那条断言必然为假。
- `TaskInspector.parse()` / `focusSnapshot()`：用真实 `dumpsys` 片段做夹具，包括**解析失败降级**（返回空列表而不是崩）（`TaskInspectorTest`）。

**不能单测的**（必须真机）：ICU 正则行为、shell 命令可用性、窗口/resize/焦点行为、ROM 的手势与权限差异。

**调试通道**：
- `diag.log`：每条 shell 命令、每次重排/交还都记一行（带时间戳）。排障第一手证据。
- `adb shell dumpsys activity activities | grep -E "topDisplayFocusedRootTask|topResumedActivity|mBounds"`
- `adb shell dumpsys activity recents`（查最近任务卡片）
- `adb shell dumpsys dropbox --print`（崩溃兜底）
- 调试启动参数：1.0 里**没有保留**；要用时按上一行的思路，给"启动 / 浮出 / 收回"各加一个 `--ez` 入口，方便脚本化复现。

## 11. 给 AI 的开工提示词模板（可直接粘贴）

```text
【任务】用 Kotlin + Jetpack Compose 从零做一个 Android 应用，在 HyperOS 4 / Android 17 手机上实现：
把一个横屏手游放到后台"隐形保活"，一键浮出成浮窗可用、一键收回、一键彻底关闭。

【硬约束】
- 唯一的特权来源是 Shizuku（shell, uid 2000），不用 root；所有系统动作都通过 shell 命令完成。
- 不许用画中画、虚拟屏、副屏、多开、分屏；不许平铺多个窗口（真机实测不可用）。
- 目标应用可能在手机分身里（userId 999），所有启动/查询命令都要带正确 --user。
- 界面只有一页：启动 / 关闭 / 更换 / 状态 / 三行权限；不出现技术名词。

【验收标准】
1. 点"启动"→ 目标应用缩成右下角 2×2 像素，进程不被冻结（游戏不卡、网络不断）。
2. 点悬浮 Dock 图标 → 浮窗 = 可用区 3/4 宽、16:9、居中，可正常操作；再点回到 2×2。
3. 浮出/收回都用"两步摆位"：先摆到目标 3/5 尺寸，350ms 后再摆到目标。
4. 每 2 秒跑一次看门狗：把跑偏的自由窗口拉回目标矩形（两步摆位）。
5. 看门狗同时做"焦点交还"：若受管窗口被系统顶成前台焦点任务，就发一条
   `am task focus <显示级 topResumedActivity 的 t<id>>` 把焦点还给用户；不动几何；3 秒冷却；浮出态和横屏不介入。
6. 点"关闭"：对每个受管包 `am force-stop [--user N] <包名>`，并对 force-stop 之前取到的任务 id 发 `am stack remove <id>`。
7. 装机后能自查三样：Shizuku(shell uid 2000)、悬浮窗权限、通知权限；点哪行跳哪行系统设置。

【必须避开的坑】
- 不要用 `am start --bounds`（本机抛 NumberFormatException）；用 `--windowingMode 5` + 事后 `am task resize`。
- `am task resize` 参数是四个空格分隔的数字。
- 不要用 `am task remove`（不存在）；清卡片用 `am stack remove <taskId>`，且 taskId 要在 force-stop 前取。
- 不要用 `settings put system user_rotation` 锁屏幕方向（本机无效）。
- 不要假设 `am help` 没列的子命令不可用（`am task focus` 就没列但可用）；也不要假设列了的都可用——一律实测。
- 所有正则包一层"编译失败就永不匹配"的兜底（ICU 正则在真机会直接抛异常闪退，JVM 单测测不出来）。
- 取命令行结果要自己轮询 `exitValue()`，不要用 `waitFor(timeout, unit)`。
- 单应用场景的目标矩形必须特判成 2×2 小点，否则看门狗会每 2 秒把它放大弹出。
- 看门狗要放过"用户手动浮出的那个窗口"，并按当前窗口顺序决定谁置顶。

【工程骨架】单模块 :app；文件划分与职责见下（照这个结构写）：
App / MainActivity / ui.WorkbenchRoot / service.WorkbenchService / service.DockView / service.BootReceiver /
window.WorkbenchController（大脑） / window.LayoutEngine（纯函数+单测） /
system.FreeformController（shell 动作） / system.TaskInspector（dumpsys 解析+单测） / system.ScreenMetrics /
system.KeepAlive / system.Diag / shizuku.ShizukuGateway / shizuku.ShellRunner / apps.AppCatalog /
data.SceneStore / model.Models

【工作方式】
- 按里程碑推进：M0 空壳能装 → M1 Shizuku 通道 → M2 读状态 → M3 起窗口 → M4 摆位 → M5 隐形保活 →
  M6 看门狗与焦点交还 → M7 悬浮 Dock → M8 界面与关闭。**每完成一个里程碑就停下来**，
  给出"验证命令 + 预期输出"，等真机确认后再继续。
- 写任何系统交互前，先把它做成可脚本触发（启动参数），不要依赖手动点按来复现问题。
- 把每条 shell 命令和每次窗口校正写进 diag.log。

【交付物】可编译安装的 APK + 一份开发文档（本文档就是模板）。
```
