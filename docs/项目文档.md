## 1. 项目介绍

### 1.1 一句话定位

**须弥芥子**是一个自用的 Android 小工具：把**一个**选定的 App 用系统「自由窗口」启动后缩成 **2×2 像素、整块落在屏幕外**的隐形小窗，让它在后台**继续运行不被冻结**；桌面上常驻一条悬浮图标，点一下就把它**弹出成浮窗**看和操作，再点一下收回；「关闭」= 结束这个 App 并连它在"最近任务"里的卡片一起摘掉。

明确**不做**的事：不是应用多开、不是虚拟屏、不是游戏加速器、不做多窗口平铺。整个应用只有一个界面。

### 1.2 目标场景（最终形态）

- 挂机 + 偶尔看一眼：横屏手游（如《洛克王国：世界》）丢在后台持续跑，需要时一键弹出、横屏正常操作，收回后继续挂。
- 挂机对象可以是**主系统**里那份，也可以是**手机分身（小米 XSpace，Android 用户号 999）**里那份。同一安装包在两个用户里的**包名完全相同**，所以场景里必须记住用户号，否则会抓到主系统那份（真机踩过）。
- 界面必须极简：一页，三个按钮。

### 1.3 功能清单

首页（唯一一页）：

| 元素 | 行为 |
|---|---|
| 当前挂机应用 | 显示所选 App 名称；若来自分身，显示「…（分身）」 |
| 状态 | 「运行中 / 未运行」 |
| **启动** | 把所选 App 以自由窗口启动 → 立即缩成**屏幕外**的 2×2 隐形小点保活 |
| **关闭** | 结束该 App（`am force-stop --user 0/999`，按「包名 + 用户号」精确到主系统或分身**那一份**）**并摘掉它的后台卡片**（`am stack remove`），收起悬浮图标条 |
| **更换** | 从已安装应用里挑，**包含手机分身里的应用** |
| 权限 / 连接 | 三行状态：Shizuku（含 `shell (uid=2000)`）、悬浮窗权限、通知权限；点哪一行跳哪一行的设置 |

悬浮图标条（Dock，浮在所有应用之上）：

| 元素 | 行为 |
|---|---|
| 应用图标 | 点一下**浮出**浮窗（可看可操作），再点一下**收回**成屏幕外的 2×2 小点继续运行 |
| 主页 | 收回浮窗并回到工作台主界面 |

后台自动行为（用户无感，但决定好不好用）：

- 每 2 秒校正一次窗口几何（看门狗）。
- 转屏后自动重排（横屏游戏切横屏不会乱）。
- 受管窗口被系统"顶成前台焦点任务"而现形时，自动把焦点交还回去 —— 只发一条 `am task focus`，**不动几何**，所以不会弹窗、不会变形（3.6 的核心）。
- 单应用（隐形小点）模式下**不再每拍抢前台**：窗口在系统眼里仍然可见时，一次都不发 `am task focus`，只在真的看不见时兜底补一次（1.1）。否则看门狗每 2 秒把挂机窗口顶到前台并抢走输入焦点，**手势导航的侧滑返回会被那颗 2×2 小点吃掉**。

### 1.4 实现路径

一条链，从上到下：

1. **特权通道**：用户在 Shizuku 里授权本应用（本机是 `shell (uid=2000)`）→ `ShizukuGateway` 判断"binder 活着 + 已授权"，`ShellRunner` 负责真正跑命令。
2. **启动**：`am start --windowingMode 5`（自由窗口）启动所选 App，带 `--user 0/999` 区分主系统与分身。
3. **摆位**：用 `am task resize <taskId> l t r b` 把窗口摆到目标位置。浮窗采用**两步摆位**（先到目标尺寸的 3/5，350 毫秒后再到目标尺寸），一次性摆位在这台 ROM 上会失效。【实测】
4. **收回成隐形保活**：`am task resize` 到**屏幕外**的 `2×2` 像素（真实屏幕右下角再往外 16 / 34 像素）。窗口仍然"可见"，所以系统不冻结它——这就是保活的全部原理；而"可见"是看窗口状态、不看坐标，所以整块挪到屏幕外也不掉保活，屏幕上还彻底看不见它（含系统画的标题栏）。
5. **悬浮图标条**：`SYSTEM_ALERT_WINDOW` 权限 + `WindowManager` 添加悬浮窗，显示所选 App 的图标和「主页」。
6. **看门狗**：`WorkbenchController.reconcileTick` 每 2 秒读一次 `dumpsys` 校对窗口；旋转、被系统改动时 `forceReconcile` 立刻重排。
7. **焦点交还**：受管窗口一旦成为 `topDisplayFocusedRootTask`（会现形/变形），只发一条 `am task focus <用户此刻真正在看的任务>` 把焦点还回去。1.1 起单应用小点模式下不再每拍主动顶前台，只在窗口真的不可见时才补一次。

### 1.5 最终形态受哪些硬约束

| 约束 | 说明 |
|---|---|
| 保活必须"可见" | 纯后台运行的 App 会被系统暂停：单机游戏卡住、网络会话掉线。【实测】所以保活载体必须是"可见但看不见"的 2×2 小窗（整块放在屏幕外也算可见），不能是纯后台 |
| 只能用 `--windowingMode` + `am task resize` | 这台 ROM 不支持 `am start --bounds`（会 `NumberFormatException`）。【实测】 |
| 系统会给可见自由窗口画标题栏 | 就是以前桌面上那个"小角"（caption bar，系统绘制、应用去不掉）。1.1 起把 2×2 小点整块放到**屏幕外**，它跟着一起出去，屏幕上就再也看不见了【实测】 |
| 同一 App 的两个用户副本必须区分 | 靠 `--user 0/999`；场景里存 `Slot.userId`【实测】 |
| 悬浮窗权限是硬门槛 | 没有 `SYSTEM_ALERT_WINDOW`，图标条完全不会创建 |

### 1.10 名词表

| 名词 | 含义 |
|---|---|
| 自由窗口 | Android 的 freeform 窗口模式（`--windowingMode 5`），窗口可自由摆放、可缩放 |

| Dock / 悬浮图标条 | 常驻在屏幕边缘的悬浮窗，用来一键浮出/收回/回主页 |

| `diag.log` | 应用自己落盘的诊断日志；本机 `logcat` 常被抽干，排障主要靠它 |

### 2.1 设备与显示

| 项 | 值 |
|---|---|
| 机型 / 系统 | Xiaomi 25098PN5AC，HyperOS 4（Android 17），OS 版本 4.0.0.41 |

### 2.2 权限底座

| 项 | 说明 |
|---|---|
| 特权来源 | Shizuku（包名 `moe.shizuku.privileged.api`），本机授权身份是 **`shell (uid=2000)`**，不是 root |
| 应用侧需要的三样 | ① Shizuku 授权；② `SYSTEM_ALERT_WINDOW`（悬浮窗）；③ 通知权限 |
| 改包名之后 | 三样**全部要重给**：Shizuku 授权要重批；`appops set com.miniworld SYSTEM_ALERT_WINDOW allow` 不给的话**图标条完全不会创建**；`pm grant com.miniworld android.permission.POST_NOTIFICATIONS` |
| 安装偶发失败 | `INSTALL_FAILED_USER_RESTRICTED`，重试一次通常就成功 |

### 2.3 shell 命令在这台 ROM 上的可用性

| 命令 | 可用 | 说明 |
|---|---|---|
| `am start --windowingMode 5` | ✅ | 以自由窗口启动应用 |
| `am task resize <id> l t r b` | ✅ | **四个分开的数字**；写成逗号串会抛 `NumberFormatException: For input string: "0,0,540,1200"`（栈顶 `ActivityManagerShellCommand.getBounds`） |
| `am task focus <id>` | ✅ | 置顶/交还焦点，是焦点交还用的唯一动作 |
| `am start --bounds l,t,r,b` | ❌ | 这台 ROM 不支持，会抛上面那个异常 |
| `am task remove` | ❌ | 这个子命令不存在 |
| `am stack remove <taskId>` | ✅ | 摘掉"最近任务"里的卡片（实测卡片数 1 → 0） |
| `am force-stop [--user N] <包名>` | ✅ | 结束应用；**但不会摘掉后台卡片** |
| `dumpsys activity activities` | ✅ | 任务、窗口、焦点状态的唯一来源 |
| `pm list users`、`cmd package query-activities --brief --user 999 …` | ✅ | 用来列出手机分身里的应用 |
| `settings put system user_rotation`、`wm user-rotation lock` | ❌ | 都锁不住屏幕方向（shell 没有这个能力） |
| `screencap -p` | ✅ | 多显示时需加 `-d 0` |

### 2.4 观测手段（排障时看什么）

| 手段 | 能看到什么 |
|---|---|
| `dumpsys activity activities` | 任务树、`mBounds`、窗口 `Requested w/h`、`topDisplayFocusedRootTask`、`topResumedActivity` |
| `dumpsys window` / `dumpsys display` | 旋转与显示列表、`InsetSource: type=captionBar … visible=true`（系统给自由窗口画的标题栏，也就是以前桌面上那个"小角"的来源） |
| `dumpsys SurfaceFlinger --list` | 图层列表（确认窗口有没有真的存在） |
| `adb shell dumpsys dropbox --print` | 崩溃记录。**本机 `logcat` 的 main/crash 缓冲经常被抽干**，只能靠它 |
| 应用自落盘的 `diag.log` | 最可靠的一手记录：每次重排、每次焦点交还、每条**失败**的 shell 命令都会记（1.11 起正常的 shell 命令不再逐条落盘），另外每 5 分钟一条"看门狗心跳" |
| `uiautomator dump` | ❌ 本机不可用（坏），所以脚本点按只能靠盲坐标，很不稳 |

## 3. 机制

每条按 **现象 → 原因 → 做法 → 证据** 写。

### 3.1 保活靠"可见"

- **现象**：App 完全退到后台，看起来还在，其实已经不动了。
- **原因**：后台进程会被系统暂停（PAUSED），单机游戏执行逻辑停住、网络会话超时掉线。
- **做法**：不让它真的退到后台——把窗口缩成 **2×2 像素**，并整块挪到**屏幕外**（真实屏幕右下角再往外 16 / 34 像素）。对系统来说窗口**仍然可见**，所以不冻结；而"可见"看的是窗口状态、不是坐标，所以挪到屏幕外并不掉保活，屏幕上还连系统画的标题栏一起看不见了。
- **证据**：【实测】纯后台方案（App 完全退到后台、不占任何窗口）被用户实测否决：游戏卡住、会话掉线；改成 2×2 小点后同场景可以长时间挂机。

### 3.2 自由窗口在这台 ROM 上的行为

- **怎么起**：`am start --windowingMode 5`，任务会带上 `mode=freeform`。
- **系统会画标题栏**：自由窗口上方那条 caption bar 是系统绘制的（`dumpsys window` 里能看到 `InsetSource: type=captionBar`），**应用无法去掉**。以前它就是桌面上那个"小角"；1.1 起把小点整块放到屏幕外，它跟着一起出去，屏幕上就再也看不见了【实测】。
- **窗口会互相影响**：同一时间前台的自由窗口只有一条，其他窗口会被挤到后面；这也是"谁拿着焦点"如此重要的原因。

### 3.3 焦点归属决定窗口是否现形（3.6 的全部依据）

- **现象**：只要别的全屏任务上来（回到桌面、打开一个竖屏 App、上滑看最近任务），那个 2×2 保活窗口就会**自己冒出来**、带上标题栏、变形，而且收不回去。
- **原因**：这台 ROM 会把这个受管窗口顶成**前台焦点任务**（`topDisplayFocusedRootTask` 指向它）。窗口一旦"被聚焦"，系统就把它按可见窗口重新显示出来。所以问题**不在几何，在焦点**。
- **关键实测**：坏掉的时候去 dump，**窗口 `Requested` 尺寸、任务 `mBounds` 全都还是 2×2**——一切"比几何"的判据都判不出来。这是被否决的那版方案失败的根本原因。
- **判据**：`topDisplayFocusedRootTask` 里的包名属于被托管的应用，而用户此刻看的（显示级 `topResumedActivity` 的 `t<任务号>`）是**别的**任务 → 判定"焦点被抢"。
- **做法**：只发**一条** `am task focus <用户此刻在看的任务>`，**几何一个字都不动**。恢复后窗口自然回到隐形状态。
- **证据**：【实测】手动执行 `am task focus 1`（桌面根任务）后 3 秒，屏幕完全干净、变形窗口消失，全程没有 resize；装到 3.6 后用户复测：不再弹窗、不再变形。
- **保护**：交还动作有 3 秒冷却，且只在"小点模式 + 竖屏"时动手——浮窗状态不碰（那时它本来就该拿焦点），横屏时不介入。**1.1 起还有一条更重要的**：单应用（小点）模式下看门狗**不再每拍主动把受管窗口顶到前台**，只在它真的不可见时才兜底补一次——因为 `am task focus` 会连带抢走输入焦点。

### 3.4 两步摆位

- **现象**：`am task resize` 一次到位时，窗口经常停在旧位置/旧尺寸，或者干脆没反应。
- **做法**：分两步——先摆到目标尺寸的 **3/5**，等 **350 毫秒**，再摆到目标尺寸。
- **证据**：【实测】这是"浮窗能不能用"的分水岭；浮出与收回两条路径都走这个流程。

### 3.5 横屏自愈、竖屏不自愈

- **现象**：横屏游戏里怎么操作都不容易坏；竖屏 App 切回桌面才容易触发 3.3。
- **原因**：转屏会触发系统重新布局，应用侧也能收到配置变化并立刻重排（`forceReconcile`）；而竖屏下"回桌面"不会触发这套重排，只会把焦点挪走。
- **做法**：转屏走重排，焦点被抢走 3.3 的交还逻辑——两条路各管一段。

### 3.6 「关闭」为什么是两条命令

- **现象**：点关闭后 App 没了，但"最近任务"里的卡片还在。
- **原因**：卡片是**任务记录**，不是进程；`am force-stop` 只杀进程。
- **做法**：先 `am force-stop [--user N] <包名>`，再用 `am stack remove <taskId>` 摘掉卡片。
- **证据**：【实测】卡片数 1 → 0；而且这台 ROM 上任务被摘掉时进程也会一起退出。

### 3.7 看门狗

- **做法**：`reconcileTick` 每 **2 秒**跑一次 `reconcileBounds()`：读任务列表 → 按槽位把窗口摆回目标几何 → 把"当前应该在前台的那个"置顶 → 交还被抢走的焦点。旋转或异常时 `forceReconcile()` 立刻补跑一次。
- **注意**：它读的是真实系统状态，所以只做"发现不对就纠正"，不做状态假设。

## 4. 数据流与「改哪里」速查

### 4.1 点一下 Dock 图标，到底发生了什么

```
手指点图标
  → DockView 回调
  → WorkbenchService（前台服务持有控制器）
  → WorkbenchController.onDockTap()
  → 读一次系统状态（dumpsys，判断现在是小点还是浮窗）
  → 浮出：am task resize（先 3/5 尺寸）→ 350ms → am task resize（目标浮窗矩形）→ am task focus（带到前台）
     收回：am task resize（缩回屏幕外的 2×2）→ 把焦点交还给用户原本在看的任务
  → 之后每 2 秒的看门狗继续校正几何
```

### 4.2 「启动」与「关闭」

- **启动**：`WorkbenchController.start()` → `FreeformController.launch(...)`（`am start --windowingMode 5`，带 `--user 0/999`）→ `TaskInspector.waitForTask()` 等任务出现 → 摆位到屏幕外的 2×2 小点 → 记进 `LiveWindow` 列表 → 服务开始渲染 Dock。
- **关闭**：`WorkbenchController.stop(killApps = true)` → 对每个「包名 + 用户号」目标 `FreeformController.closePackage()`（`am force-stop --user 0/999` + `am stack remove`）→ **等收工真正跑完**再停前台服务 → 移除 Dock。

### 7.1 主线

| 阶段 | 做了什么 | 结果 |

### 7.2 死路清单（负知识，避免重复踩）

| 想法 | 实测结果 | 为什么不行 |
|---|---|---|
| 关闭时只写包名、不带 `--user` | 装有手机分身的应用**两份一起被杀**（真机踩过） | 条件是"同名包 + 另一个用户"两个；不带 `--user` 会命中所有用户里的同名包，必须永远显式写 `--user 0/999` |
| 撤销保活用 `am set-standby-bucket <pkg> default` | 直接 `Error: Unknown bucket: default`（`exit=255`） | 合法桶只有 `active`/`working_set`/`frequent`/`rare`/`restricted`，没有"默认"；也不硬塞 `rare`（那等于主动降级） |
| 停服务时用 `shutdownNow()` 顺手收尾 | 收工第一条 `dumpsys activity activities` 抛 `InterruptedException`，卡片摘不掉（`diag.log` 写"摘掉 0/0"） | 它打断的正是"正在按 taskId 摘卡片"的工作线程；收工要等它跑完（`shutdown()`），并给"现场查不到"留退路 |
| 自由窗口平铺多个 App | 小窗浮在主窗上、主窗不放大、背后黑 | 用户否决；且这台 ROM 不支持 `am start --bounds` |
| 纯后台保活（不占窗口） | 后台进程被暂停，游戏卡住、会话掉线 | 保活载体必须"可见"，哪怕只有 2×2 像素 |
| `am start --bounds` 指定位置 | 抛 `NumberFormatException` | 该参数在这台 ROM 上不被支持，只能用 `--windowingMode` + `am task resize` |
| `am task remove` 摘卡片 | 子命令不存在 | 要用 `am stack remove <taskId>` |
| 把窗口挪到屏幕外隐藏（1.0 时的推断） | **推断错了**：1.1 实测 `am task resize 1236 2690 1238 2692`（屏幕 1220×2656）被原样接受，任务仍 `visible=true`、进程仍 `curProcState=2`（TOP、不冻结），屏幕上的 caption bar 也一起看不见 | 结论：判"可见"看的是窗口状态、**不是坐标**；唯一副作用是"回桌面"那一下系统会把窗口搬回屏幕中间，看门狗 2 秒内扔回屏幕外即可 |
| 每 2 秒对受管窗口发一条 `am task focus` 来"置顶/保活" | 手势导航的侧滑返回被那颗 2×2 小点吃掉（挂机后侧滑回桌面几乎不生效） | `am task focus` 在这台 ROM 上 = 顶前台 + **抢走输入焦点**；而保活本来不需要焦点（实测：不 focus 也一直 `curProcState=2`） |
| 用画中画（PIP）当保活载体 | nrc 的 PIP 支持查不到；PIP 是缩略窗、操作受限 | 【推断】不适合"要能正常操作"的挂机场景 |
| 用第二显示（`displayId 1`）当保活载体 | 该显示 `state OFF`，且带 `FLAG_PRESENTATION` | 关闭状态，不能承载应用窗口 |
| 自建虚拟显示（VirtualDisplay） | shell 没有 `CREATE_VIRTUAL_DISPLAY` 权限 | 要做只能走 `MediaProjection`（未验证） |
| 锁定屏幕方向 | `settings put system user_rotation` 与 `wm user-rotation lock` 都无效 | shell 没这个能力；改成"不锁方向，靠重排 + 焦点交还各自处理" |
| 定期把窗口重钉成 2×2（3.5） | 会抢焦点、横屏把人踢回桌面 | 交还目标选错（挑"第一个不是我们、也不是受管应用的任务"），且动作太粗暴 |
| 用几何数值判断"窗口是否被系统还原" | 坏的时候窗口 `Requested` 与任务 `mBounds` 完全正确 | 判不出来——这是本项目最大的一条教训 |
| 用 `uiautomator dump` + 坐标点按做自动化测试 | 本机 `uiautomator dump` 是坏的，盲点按经常点不中 | 改为给应用留调试启动参数，用命令直接触发 |

## 8. 经验总结

1. **判据要看语义状态，不要只看数值。** "窗口是不是被系统还原了"，几何完全看不出来，看"谁拿着焦点"一眼就中。3.5 失败与 3.6 成功，差别只在这一处。
2. **判据必须用真机 dump 定，不能靠推断。** 同一个现象能推出好几种"合理"结论，只有 dump 能判定哪一种成立。
3. **破坏性动作最小化。** 3.6 全程只发一条 `am task focus`，不动几何——改得越少，横屏这些别的路径越不容易被牵连。
4. **shell 权限不等于无所不能。** 锁方向、建虚拟显示、`--bounds` 摆位都做不到；设计路线前先验证能力，别先设计后碰壁。
5. **真机特有的坑要写在代码里。** 例如 `am task resize` 只吃空格分隔的四个数字；正则一律走 `rx()`（ICU 正则在真机会直接抛 `PatternSyntaxException`，JVM 单测测不出来）；取命令结果用轮询 `exitValue()`（`waitFor(timeout)` 会把 Binder 异常变形）。
6. **留好一手证据链。** 本机 `logcat` 经常被抽干，所以应用自己落盘 `diag.log`（每条命令、每次重排都记），崩溃再兜 `dumpsys dropbox --print`。
7. **给调试留可脚本触发的入口。** 不要依赖"点按钮"来复现问题（本机点按不可靠），用启动参数直接触发某条路径。（1.0 清理时把当时那几个入口删掉了，需要时再加回。）
8. **版本纪律。** 用户确认才记版本号；效果待定的试验包不进版本表；每个接受版出快照、记 APK 大小与 sha256、并把 APK 推到手机。1.0 起为正式版，之前的 3.0–3.6 记为测试版。
9. **"隐形"和"可见"是两件事。** 系统判"可见"看的是窗口状态（`visible=true`、`mViewVisibility=0x0`），与坐标无关；所以把 2×2 整块放到屏幕外，既保住了保活、又让系统画的标题栏一起出了屏幕。（1.0 时这条被想当然地判成"不行"，1.1 实测推翻。）
10. **命令的副作用比它的名字重要。** `am task focus <id>` 名字像"设个焦点"，实际会顶前台 + 抢走输入焦点——看门狗每 2 秒调它一次，就足以让手势导航的侧滑返回稳定失效。凡是要写进周期的命令，先把它单独跑一遍，看它对"焦点 / 前台 / 几何"到底动了什么。
