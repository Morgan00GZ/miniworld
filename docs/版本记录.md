# 版本记录（须弥芥子）

命名规则：**1.0 是第一个正式版**（**1.01 是 1.0 的改名版**，2026-10-12；**1.02 是 1.01 的修复版**，2026-10-13）；此前的 **3.0 – 3.6 全部记为测试版**（v1/v2 是更早的开发期历史版本）。

**快照规矩（2026-10-12 起，A 方案）**
- **凡是被赋予版本号的版本，都留一份快照**（不再"只留最近两个"）。
- 快照放在本仓库的 `snapshots\<版本>\` 下，是**当时工程的整份拷贝**（源码 + 文档 + 工具 + 该版本的 APK 副本），并打一个**同名 git tag**（`1.0`、`3.6`）。`.gitignore` 里显式放行 `snapshots/**/*.apk`，所以"这一版能原样装起来"的 APK 会跟着仓库走。
- **加快照时 APK 要 `git add -f`**：快照目录里会连当时的 `.gitignore` 一起拷进去，里面那条 `*.apk` 比仓库根目录的放行规则更"深"、优先级更高，会把快照 APK 悄悄挡住（1.01、1.02 都踩过这个坑）。加完用 `git ls-files snapshots/ | findstr /i .apk` 核对一遍。
- 1.0 之前的老快照放在仓库外的 `onestep-workbench-snapshots\`，**已按要求清理，只留文字记录**（见文末"历史快照一览"）。

**这一版包含的关键修复（都是真机验证过的，别回退掉）**：

1. Shizuku `newProcess` 返回的进程对象 `waitFor(timeout)` 有坑（异常类型经 Binder 变形成 `IllegalArgumentException`）→ 改为自己轮询 `exitValue()`。
2. 浮窗刚弹出时渲染错乱（游戏按钮丢失、触控失效）→ **两次摆位**（先 3/5 尺寸，350ms 后再到目标）触发配置变化。**这是整个方案能用的分水岭**。
3. 横屏浮窗尺寸：`ScreenMetrics` 取的是自然方向尺寸，横屏时必须把长边当宽用。
4. 收起状态下转屏会自己弹出 → `WorkbenchService.onConfigurationChanged` + 2 秒看门狗立刻校正。
5. 看门狗校正要按**当前窗口顺序**，否则会把用户的选择掰回去。
6. `am force-stop` 会让系统**补发排队的 BOOT_COMPLETED**，导致"只打开工作台却自动开工" → 已停用开机自启分支。
7. 启动命令一律显式带 `--user N`（`FreeformController.amStart()`），否则有分身的应用会弹"选哪一个"。

## ⚠️ 改包名之后必须重新给的三样东西（3.1 踩过的坑）

改 `applicationId` 等于在系统里装了一个**全新应用**，下面三样都**不会**跟过来：

| 需要重给 | 症状 | 怎么给 |
|---|---|---|
| Shizuku 授权 | 点「启动」没反应 | 在 Shizuku 里授权，或点 App 里那行 Shizuku 状态 |
| **「显示在其他应用上层」** | **图标条完全不出现**（代码里缺这个权限就直接不创建 Dock） | `adb shell appops set <包名> SYSTEM_ALERT_WINDOW allow`，或设置里手动开 |
| 通知权限 | 常驻通知不显示 | `adb shell pm grant <包名> android.permission.POST_NOTIFICATIONS` |

**排查口诀**：图标条不出来 → 先查 `cmd appops get <包名> SYSTEM_ALERT_WINDOW` 是不是 `allow`；
再查 `dumpsys activity services <包名>` 有没有在跑；最后看 App 自己落盘的 `diag.log`。

真机结论（HyperOS 4 / Android 17，用「设置」做的样本）：

- `am force-stop` 单独用**不会**去掉卡片：force-stop 之后 `dumpsys activity recents` 里仍有一条 `* Recent #1: Task{... A=1000:com.android.settings.root}`。
- 这台机器**没有** `am task remove`（`Error: unknown command 'remove'`）；能删卡片的是 **`am stack remove <rootTaskId>`**：对 787 发一次，卡片数 1 → 0。现代 Android 每个标准任务自己就是 root task，所以任务 id 可以直接当 stack id 用。
- 任务 id 必须在 force-stop **之前**取：force-stop 之后任务就从活动列表里消失，再查就查不到了。
- 只 `am stack remove` 不发 force-stop（= 手动划卡片）：这台机器上普通应用连进程一起死（`pidof com.android.settings` 6517 → 空），但带前台服务 / 被 bind 的应用划走后进程可能还活着，所以两条都发。

自测记录（如实写）：机制、编译、传参接线（`WorkbenchRoot.kt:138` → `WorkbenchService` `EXTRA_KILL` → `WorkbenchController.kt:630 stop(killApps=true)` → `closePackage`）都验过；**端到端 UI 点按脚本没跑通**（本机 `uiautomator dump` 坏、盲点按坐标不稳，几次都没点中按钮），最终由用户实测确认：关闭成功、后台卡片消失。

真机实测结论：

- 坏状态的**唯一可靠信号是"谁拿着焦点"**：实测坏的时候任务矩形和窗口 `Requested w=2 h=2` **全都正常**，所以任何比几何的判据都判不出来（这是废弃的 3.5 失败的原因）。
- 只发一条 `am task focus <桌面根任务>` 就能让坏窗口立刻消失（全程无 resize）。
