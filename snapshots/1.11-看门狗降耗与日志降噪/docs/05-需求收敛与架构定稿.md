# 05 · 需求收敛与架构定稿

> **修订记录**
> v1（前一轮）：不做应用分身/多开（OS 已提供）。
> **v2（本轮）：后台 App 必须绝对实时保活，但不需要实时小窗预览；切换入口简化为纯图标。**
>
> v2 的两条修正都指向同一个方向：**去掉一切"给用户看"的图形工作，只保留"让 App 活着"的最小机制。**
> 结果是架构比 v1 更简单、更省电，而且**关键假设不用写 App 代码就能验证**（见第 5 节）。

---

## 0. 最终需求

| 项 | 内容 |
| --- | --- |
| 要 | 不在前台显示的 App **持续实时运行**（逻辑与渲染都不停）、进程不被冻结/杀死；用**应用图标**一键把任意一个切到前台 |
| 不要 | 应用分身/多开（OS 已有）；**实时小窗预览**（不占屏、不耗额外性能） |
| 场景 | 多个游戏挂机 + 看视频 |
| 约束 | 只用 Shizuku（不 root、不 LSPosed） |

## 1. 两个必须先接受的事实

### 1.1 "运行"分两层，而第二层必须"可见"

| 层次 | 含义 | 手段 |
| --- | --- | --- |
| 进程层保活 | 不被冻结、不被杀，能收包、跑定时器 | shell 保活命令（**已实现**） |
| **Activity 层保活** | 不被 `PAUSE`/`STOP`，**继续渲染、继续推进游戏逻辑** | 必须让窗口"可见" |

Android 判定"可见"是按窗口来的：一个全屏 App 会盖住其它窗口，被盖住的窗口就不可见 → `PAUSE` → `STOP` → 冻结。
所以「一个全屏 + 其它继续跑」在普通窗口模型下**不存在**，只有三条通路：

| 通路 | 多个 | 不占屏 | 继续跑 | 本机实测状态 |
| --- | --- | --- | --- | --- |
| **虚拟屏** | ✅ | ✅ | ✅ | 建屏 OK；**往系统屏启动被权限拒**（P18.3）→ 须自建 VirtualDisplay（M2-2） |
| **小窗 / 分屏（Freeform）** | ✅ | ❌ | ✅ | **已实测通过**：起得来 + 改得动 + 前置得了（P2/P3/P4） |
| 画中画 PiP | ❌（全局仅 1 个） | ✅ | ✅ | 未测 |

→ **虚拟屏是唯一同时满足"多个 + 不占屏 + 继续跑"的机制**，但它现在是**可选增强**；
**不打折扣的"多个 + 继续跑"已经能用 Freeform 同屏平铺做到**（代价是占屏，见第 2 节档位表）。

### 1.2 帧消费不能省——但"不显示"可以

这一条容易被误解成"不要小窗 = 不要开销"，其实不是：

- 虚拟屏是一块**真的显示设备**，App 在里面正常渲染；
- 如果**没有任何消费者**读走画面，缓冲区队列（约 3 帧）满了之后，App 的渲染线程会**阻塞在 `eglSwapBuffers`**——
  表现出来的就是**卡死**，比被暂停更糟；
- 所以必须挂一个消费者，**把帧读走再丢掉**（`ImageReader` + `acquireLatestImage()` + `close()` 即可，不需要 GL、不需要画到屏幕上）。

**结论**：`不要小窗预览` 省掉的是"渲染到屏幕 + 触摸转发 + 输入法转发"这一整条链路（这是最复杂、最容易碎的部分），
但**省不掉虚拟屏本身的渲染与合成**。真正的省性能手段见第 4 节。

## 2. 架构定稿（v2）

```
┌─ 工作台（一个前台服务 + 纯图标悬浮条）────────────────────────┐
│                                                              │
│  主屏 = 真实主屏                                              │
│     · 当前选中的 App 原生全屏运行                             │
│     · 输入法、相机、横屏、DRM 全部走原生路径 → 兼容性风险最低  │
│                                                              │
│  副槽 = 1~3 个虚拟屏（不显示、无预览）                         │
│     · 每个槽承载一个后台 App，保持 RESUMED，继续跑             │
│     · 挂一个"读帧即丢"的消费者，防止生产端阻塞                 │
│                                                              │
│  一键切前台 = 任务在「主屏 ↔ 副槽」之间交换                     │
│     · 是搬任务，不是重启 App；进度/登录态原地保留              │
│                                                              │
│  切换入口 = 纯图标 Dock（已有实现，去掉一切缩略图）             │
│                                                              │
│  保活 = shell 命令叠加（白名单 / 待机桶 / appops / 冻结器）     │
└──────────────────────────────────────────────────────────────┘
```

**v2 相比 v1 去掉了**：SurfaceView 画面镜像、按 displayId 的触摸注入、输入法转发、实时缩略图。
这四项正好是 Shizuku-only 方案里最容易碎的部分。

### 2.1 档位表（真机实测后更新）

| 档位 | 机制 | 用途 | 状态 |
| --- | --- | --- | --- |
| **A · 系统自由窗口平铺** | `am start --windowingMode 5` + `am task resize`（4 个分开的数字）+ `am task focus` | 多个 App 真同屏、都可见、都继续跑 | **已实测通过，作为当前主方案**（P2/P3/P4 PASS） |
| **A+ · 小米原生小窗服务 `mi_freeform`** | binder 调 `mi_freeform.startAppInFreeform` | 官方小窗手感、尺寸/DPI 精确 | **本机无该服务，作废**（P9：`service list` 查无 `mi_freeform`，HyperOS 4 已移除/改名） |
| **D · 虚拟屏后台槽** | shell 侧自建生命周期绑定的 `VirtualDisplay`；`am start --display` 放 App 上去；切换 = 跨屏搬任务 | 多个 App 同时跑 + **不占屏** + 一键切前台 | **保留为可选增强**；前置条件是 **M2-2「自建 VirtualDisplay」PoC**（**不能再用 `overlay_display_devices`**，实测被 `SecurityException` 拒，见第 5 节） |
| **D2 · 微窗** | 把自由窗口压到屏幕边缘的极小尺寸（如 64×64） | 虚拟屏不可用时仍能"可见即 `RESUMED`" | 实验备选（依赖已实测通过的 A 档通路） |
| **B · 厂商小窗** | HyperOS 自带小窗 / 迷你小窗 | 单挂机位兜底 | 系统自带 |
| **C · 保活 + 前置切换** | deviceidle / appops / standby-bucket | 进程层保活，切回即续上 | 代码已就绪（P7 实测 PASS） |

> **档位优先级的结论**：A 档已实测成立，所以"真同屏平铺"不再是"退而求其次"，
> 而是**当前主方案**；D 档从"目标档位"降级为"可选增强"——它省掉的是屏幕占用，
> 而不是可行性。A+ 档在本机作废，不要为它写 AIDL 适配。

## 3. 后台保活的三条通路（按开销从小到大）

| 通路 | 做法 | 适用 | 开销 |
| --- | --- | --- | --- |
| **P17 型：不用保活** | App 自带头台服务（`dumpsys activity services <pkg>` 有 `isForeground=true`）→ 只需要进程层保活 | 不少挂机游戏、音乐/视频 App | 几乎为零 |
| **D1 虚拟屏**（可选增强，M2-2） | **App 自建** virtual display 并把 App 放上去；App 保持 `RESUMED` | 需要持续渲染/推进逻辑、且**不想占屏**的游戏 | 一份渲染 + 合成 |
| **A 档自由窗口平铺**（主路径，已实测） | `--windowingMode 5` + `am task resize`（4 个分开的数字）+ `am task focus`；同屏即可见即 `RESUMED` | 挂机 + 看视频的**默认方案**，代价是占屏 | 一份渲染 + 合成（与虚拟屏同级） |
| **D2 微窗**（实验备选） | 把 App 的自由窗口压到屏幕边缘一个极小尺寸（如 64×64）——窗口"可见"即 `RESUMED` | 想要"接近不占屏"又不想建虚拟屏时 | 远小于虚拟屏 |
| 只做 C 档 | 进程层保活 + `am start` 前置切换 | 上述都不可用时 | 零（但 App 会被暂停） |

> **先跑 P17 再决定**：如果目标 App 自己就有前台服务，你根本不需要为它建虚拟屏（实测 `com.tencent.nrc` **没有**前台服务）。
> D2 微窗依赖 Freeform（P1–P3 **已实测通过**），且部分 App 在极小尺寸下会异常，属于"值得一试但不是主路径"。

## 4. 性能预算与旋钮（"省一点性能"具体怎么省）

| 旋钮 | 做法 | 收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| **虚拟屏分辨率** | 建低规格屏（如 540×1200 / dpi 220）而不是 1080×2400 | 像素量降到 1/4，GPU 与功耗显著下降 | 画面本来就不看；个别 App 对异常分辨率/DPI 不适 |
| **虚拟屏数量** | 建议上限 3 | 线性 | 内存与合成开销 |
| **帧消费方式** | `ImageReader(maxImages=2)` + `acquireLatestImage()` + `close()`，只丢不画 | 避免渲染线程阻塞（1.2） | 仍有一次合成 |
| **虚拟屏池化** | App 被切到主屏后它的虚拟屏就空了 → 回收，保留一个空闲屏复用 | 减少常驻屏 | 频繁建/销也有开销，建议复用 |
| **帧率 hint** | `surface.setFrameRate(30f, …)` | 可能压低生产端帧率 | 只是 hint，不保证 |
| **按需启用** | 只有场景里勾了"深度保活"的 App 才建虚拟屏 | 直接省掉不需要的 | — |

## 5. M2 的两条通路：overlay 已实测（被权限拦死），自建 VirtualDisplay 待做

### 5.1 M2-1 · `overlay_display_devices` 通路（**已实测：建屏 OK、启动被拒**）

Android 有一个现成的开发者开关：`overlay_display_devices`（"模拟副屏"）。
用 shell 写入即可让系统创建一块**虚拟屏**，而且它由系统持有（surface 也由系统处理），
**我们连帧消费者都不用写**——看起来是验证"虚拟屏能不能留住 App"的最小实验：

```powershell
# 1) 基线
adb shell dumpsys display | Select-String 'displayId' | Measure-Object -Line

# 2) 造一块虚拟屏（宽x高/dpi）
adb shell settings put global overlay_display_devices "1080x2400/440"
Start-Sleep 3
adb shell dumpsys display | Select-String 'displayId' | Measure-Object -Line   # 应该 +1

# 3) 把 App 放到这块屏上（displayId 取新出现的那个）
adb shell am start --display <NEW_ID> -n <包名>/<主Activity>

# 4) 撤销
adb shell settings delete global overlay_display_devices
```

**实测结果（Xiaomi 25098PN5AC / Android 17 / HyperOS 4.0）**：

| 步骤 | 结果 |
| --- | --- |
| P18.1 display 基线 | `displayId = 0,1`（2 个） |
| P18.2 写 `overlay_display_devices=1080x2400/440` | **建屏成功**：新增 **`displayId=7`** |
| P18.3 `am start --display 7 -n pkg/act` | **被拒**：`SecurityException at SafeActivityOptions.checkPermissions` |
| P18.5 清理 | 回到 `displayId 0,1` ✓ |

**判读（这是对旧假设的修正）**：

> `overlay_display_devices` 造出来的屏是**系统持有**的，**shell(uid=2000) 无权往它启动 Activity**。
> 所以它**不能当"后台槽"容器**——旧文档第 5 节设想的"用 overlay 屏验证 D1 通路"这条捷径**在本机不成立**。
> 旧文档还写着"PoC 用系统持有的 overlay display，生产再换成自建 virtual display，
> 但'能否 `am start --display`'这个底层假设两者相同"——**这个假设被实测否掉了**：
> 两者的权限模型不同，overlay 屏的结论**不能**外推到自建屏。

### 5.2 M2-2 · 自建 VirtualDisplay 通路（**待做，D 档的前置条件**）

D 档必须由 **App 自己创建 VirtualDisplay**：`ownerUid=2000`，走 `DisplayManager` binder / `VirtualDisplayConfig`。
只有这样，"往这块屏启动 App"才不会被 `SafeActivityOptions.checkPermissions` 拦下。

要做的事（**不写一行代码就无法再往下判断**）：

1. shell 侧（或 App 内借用 Shizuku 的 `uid=2000`）创建 public virtual display，记录它的 `displayId`；
2. 用它 `am start --display <id>` 或 binder `moveTaskToDisplay` 把 App 放上去；
3. 读任务 `state`：`RESUMED` → 通路成立；`STOPPED`/`PAUSED` → D 档不成立，退回 A 档（已实测可用）；
4. 挂一个"读帧即丢"的消费者（`ImageReader` + `acquireLatestImage()` + `close()`），防止生产端阻塞。

> 相关的调用身份前提已实测：`uid=2000(shell)`、`context=u:r:shell:s0`（P10 PASS）。
> 分辨率/数量/池化等旋钮见第 4 节。

## 8. 关于"绝对实时"的诚实说明

免 root 条件下能做到的最大值：**虚拟屏保持 `RESUMED` + 不冻结 + 电池白名单 + 待机桶 active +
本应用前台服务常驻**。但这不等于数学意义上的"绝对"：

| 仍可能中断的情况 | 说明 |
| --- | --- |
| 内存压力下的系统回收 | 虚拟屏上的 App 可见度更高，优先级比纯后台高，但不是不会被杀 |
| App 自身崩溃 / 断线 | 与本方案无关，可加"看门狗重启"作为 M5 增强 |
| 温度墙降频 | 物理限制；多屏同开时更明显（M4 要实测） |
| HyperOS 的自定义省电策略 | 可能绕过标准机制，需要引导用户在系统设置里加白名单 |
| 低分辨率虚拟屏导致个别 App 异常 | P16 实测；可按 App 覆盖分辨率 |
