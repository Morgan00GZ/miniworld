# 02 · 架构与命令映射

本文是**实现契约**：模块职责、数据模型、每一条 shell 命令的成功判定与回退链。
代码按本文件实现，本文件随代码一起改。


**分层原则**

| 层 | 允许做什么 | 禁止做什么 |
| --- | --- | --- |
| `window/LayoutEngine` | 纯计算：屏幕尺寸 → 每个 slot 的 `Bounds` | 不碰 Android 框架、不碰 shell（因此可 JVM 单测） |
| `shizuku/` | 只负责"把命令跑起来、把输出拿回来" | 不知道 Freeform、不知道场景 |
| `system/` | 把能力封装成语义方法（`launchFreeform`、`resizeTask`） | 不弹 UI、不持有 Activity |
| `service/` | 编排 + 悬浮窗 + 生命周期 | 不直接拼 shell 字符串（走 `system/`） |
| `ui/` | 展示与设置 | 不直接执行命令 |

## 3. 命令映射表（核心）

> 所有命令都以 **Shizuku（shell, uid 2000）** 身份执行。
> "成功判定"是硬条件——**没有输出判定就不算成功**，这是本方案对抗 ROM 差异的唯一办法。

### 3.1 环境与开关

| 能力 | 主命令 | 成功判定 | 回退 / 备注 |
| --- | --- | --- | --- |
| 读 Freeform 开关 | `settings get global enable_freeform_support` | **读到值即算探测成功** | 实测本机为 `0`，但 `FEATURE_FREEFORM_WINDOW_MANAGEMENT=True` → **Freeform 可用，无需修改/重启**（见下） |
| 系统是否声明 Freeform | `pm list features \| Select-String FEATURE_FREEFORM_WINDOW_MANAGEMENT` | 输出含该特性 | 有 → 开关为 0 也不用改（**本机实测就是这个情况**） |
| 写 Freeform 开关 | `settings put global enable_freeform_support 1` | 退出码 0 | **仅在既无特性、又无自由窗口时**才提示；需重启生效，App 只提示、不擅自重启 |
| 强制可调整大小 | `settings put global force_resizable_activities 1` | 退出码 0 | 本机实测已是 `1`，无需改动 |
| 冻结器状态（只读） | `settings get global cached_apps_freezer` | 读到值 | 只报告，**不修改**（全局影响）。实测本机 `freezer=disabled`，对挂机有利 |

> **实测修正（P1）**：本机 `enable_freeform_support=0` 且自由窗口**照常可用**（P2/P3/P4 全 PASS）。
> 因此自检页**不能把开关为 0 直接标成 WARN/FAIL**，必须结合
> `FEATURE_FREEFORM_WINDOW_MANAGEMENT` 一起判定——否则会给用户一条"请改设置并重启"的无用指引。

### 3.2 窗口启动

> **本机实测前提（Xiaomi 25098PN5AC / Android 17）**：`am start` **没有 `--bounds` 选项**（P0.2 ✗），
> 所以"一步到位带尺寸启动"这条捷径**不存在**，只能 **先启动 → 再 `am task resize`**。
> `--windowingMode 5` 是存在的（P0.1 ✓）且实测起得来自由窗口（P2 ✓）。

策略链**按顺序尝试，第一个成功即停**，并把成功的策略写入偏好，下次直接用：

| # | 策略名（写入偏好用的 key） | 实现 | 成功判定 |
| --- | --- | --- | --- |
| 1 | `app-launch-bounds` | App 内 `startActivity(intent, options)`：`options.setLaunchBounds(rect)`，并尽力反射 `setLaunchWindowingMode(5)` | 2.5s 内任务列表出现该包，且是 freeform 或 bounds 接近目标（±24px） |
| 2 | `shell-windowing-mode` | **`am start -n <pkg>/<act> --windowingMode 5`**（**不要**带 `--bounds`，本机无此选项） | 2.5s 内出现该包的自由窗口（实测：`taskId=91`、`mode=freeform`） |
| 3 | `fullscreen-then-resize` | `am start -n <pkg>/<act>`，等任务出现后 **`am task resize <id> <LEFT> <TOP> <RIGHT> <BOTTOM>`**（4 个分开的数字）并**复查** bounds | resize 后 bounds 确实变了（实测：`mBounds=Rect(0,0-540,1200)`） |
| 4 | `vendor-broadcast`（可选） | `am broadcast -a name.liuyi.mifreeformx.action.SWITCH_TO_FREEFORM --es component <pkg>/<act>` | 输出含 `Broadcast completed` 或 result=0（**本机未测**，依赖 Xposed 模块，P8 SKIP） |

成功的策略名会写进偏好（`working_strategy`）。下次直接跳过"App 内启动"这一档，
省掉一次注定失败的黑屏闪烁——这是"策略链"和"顺序重试"的区别所在。

补充说明：

- `am start --bounds` 在本机**不存在**（P0.2 ✗，实测 `am help` 里没有该选项）。
  旧文档写的"若 `am help` 里有 `--bounds` 就一并带上"要改成**默认不带**，
  只在探测到它存在的机型上才走这条捷径。
- 自由窗口启动成功后**默认尺寸不等于目标尺寸**（实测 P2 起来后需再 resize），
  所以**策略 2 必须跟一次 `am task resize`**，除非策略 1（App 内 `setLaunchBounds`）成功。
- 拉起前先确认目标 App 不在前台，避免 `--activity-reorder-to-front` 误触发重排。

### 3.3 任务查询（TaskInspector）

| 能力 | 命令 | 解析 |
| --- | --- | --- |
| 任务列表 | `dumpsys activity activities` | 正则抓 `Task{... #<id> ... A=<uid>:<pkg> ...}`，兼容 `mode=freeform` / `windowingMode=5` |
| 兜底列表 | `dumpsys activity recents` | 同上，字段更少 |
| 原始输出 | 全量保存到日志 | 自检页可查看原文，便于 ROM 差异排查 |

正则必须**容忍字段缺失**（不同 ROM 的 dumpsys 排版不同），解析失败时返回空列表而不是抛异常——
"解析不到"和"执行失败"是两回事，日志里要分开。

### 3.4 窗口操作

> ⚠️ **本节的命令写法必须照抄，不要"顺手压缩"。** 之前 `am task resize` 被写成了逗号串，
> 直接导致项目误判"自由窗口走不通"（见 [docs/01](01-可行性分析.md) 第 7 节）。三处 bug 的综合教训是：
> **shell 命令的"参数形状"也是契约的一部分**，写错了会伪装成"能力不支持"。

| 能力 | 主命令 | 成功判定 | 回退 |
| --- | --- | --- | --- |
| **改大小** | **`am task resize <TASK_ID> <LEFT> <TOP> <RIGHT> <BOTTOM>`**（**4 个分开的数字**） | 退出码 0 **且** 复查 bounds 已变（实测 `mBounds=Rect(0,0-540,1200)`） | 重新用策略链 1/2 以目标尺寸启动 |
| **前置** | **`am task focus <TASK_ID>`** | 退出码 0 且任务 `visible=true` / `frontOfTask`（实测输出 `Setting focus to task 91`） | `am start -n <pkg>/<act> --activity-reorder-to-front` |
| 收全屏 | `am task resize <TASK_ID> 0 0 <W> <H>` 后 `am start -n <pkg>/<act> --windowingMode 1` | 任务 `mode=fullscreen` | 仅 resize 到全屏尺寸（同样用 4 个分开的数字） |
| 关闭 | `am force-stop <pkg>` | 退出码 0 | `am kill <pkg>` |

#### ⚠️ `am task resize` 参数形状警告（**误判根因，务必保留**）

```bash
# ✗ 错误：bounds 写成单个逗号串
am task resize 91 0,0,540,1200
#   → java.lang.NumberFormatException: For input string: "0,0,540,1200"
#     （ActivityManagerShellCommand.getBounds / runTaskResize）

# ✓ 正确：4 个分开的数字，空格分隔
am task resize 91 0 0 540 1200
```

- 参数必须**恰好 4 个**：`LEFT TOP RIGHT BOTTOM`，全部是整数。
- **之前写错导致误判**：错误写法让 P0.3 与 P3 双双判 FAIL，于是"能起窗口但改不了尺寸"，
  栅格编排被判不成立 → 文档误写"只能退到档位 B/C"。改成 4 个数字后 **P3 实测 PASS**。
- 同理，**收全屏**那一行的 `0,0,<W>,<H>` 也是错的，必须写成 `0 0 <W> <H>`。
- 传参前在 Kotlin 侧做一次显式拼装，不要依赖字符串模板拼接逗号串：

```kotlin
// system/FreeformController.kt —— 参数形状的唯一定义处
fun resizeTask(taskId: Int, b: Bounds): String =
    "am task resize $taskId ${b.left} ${b.top} ${b.right} ${b.bottom}"
```

#### 关于 `am task focus`（P0.4 的一个坑）

`am task focus` 实测**可用**（`Setting focus to task 91`），但 **`am help` 并不列出该子命令**。
所以：

- **不要**用"`am help` 里有没有 `focus`"来判定它可不可用——那会得到假阴性；
- 判定方式是**实际执行一次并看输出**（失败则回退 `--activity-reorder-to-front`）；
- 自检页的 P0.4 因此标 PASS，但保留回退链以防 ROM 差异。

### 3.5 挂机保活

| 能力 | 命令 | 备注 |
| --- | --- | --- |
| 电池优化白名单 | `cmd deviceidle whitelist +<pkg>` | 幂等；`+` 前先查 `dumpsys deviceidle whitelist` |
| 待机桶 | `am set-standby-bucket <pkg> active` | Android 9+ |
| 后台运行 | `cmd appops set <pkg> RUN_ANY_IN_BACKGROUND allow` | 部分 ROM 叫 `RUN_IN_BACKGROUND` |
| 唤醒锁 | `cmd appops set <pkg> WAKE_LOCK allow` | 谨慎，默认只在用户显式开启时下发 |
| MIUI 自启动 | `cmd appops set <pkg> AUTO_START allow` | MIUI 专有 op，失败即忽略（不计 FAIL） |
| 撤销 | 以上 `+`→`-`、`allow`→`default` | 「收工」时逐条撤销，不留副作用 |

### 3.6 平台事实（Android 17 / HyperOS 4 实测，写代码前必读）

| 事实 | 实测 | 对实现的约束 |
| --- | --- | --- |
| 任务模型改名 | `am stack list` 已无 `Stack id`，输出形如 **`RootTask id=91 bounds=[0,0][540,1200] displayId=0`** | 抓任务标识**不要依赖 `Stack id`**（降级为 SKIP）；用 `dumpsys activity activities` 里的 `Task{...#<id>}`，或 `RootTask id=` |
| `displayId` 解析 | `dumpsys display` 里既有 `displayId=7`（1–3 位），也有 `mDisplayId=4630946949513469331`（19 位 token） | 正则**区分大小写** + 限定 `\d{1,3}` + `TryParse` 兜底，禁止整块匹配 `DisplayDeviceInfo{...}` |
| `am display` 必须带子命令 | 裸跑 `am display` 抛 `IllegalArgumentException: Argument expected after "display"`（`BasicShellCommandHandler.getNextArgRequired`） | **永远带子命令**；能力探测也不要裸跑 |
| `am start --display` 的权限边界 | 往 `overlay_display_devices` 造出的屏启动 → `SecurityException at SafeActivityOptions.checkPermissions` | **系统持有的 display 不能当"后台槽"**；D 档必须由 App 自建 `VirtualDisplay`（ownerUid=2000） |
| `am start --bounds` | 不存在（P0.2 ✗） | 尺寸只能事后 `am task resize` |
| `am task focus` | 可用，但 `am help` 不列出 | 用"执行一次看输出"判定，不用 help 匹配 |
| 分辨率与 dpi | 真实屏 `mMaxBounds=Rect(0,0-1220,2656)` @ **520 dpi** | `LayoutEngine` 的输入必须取**运行时实测**值，不能写死 1080×2400 |

> 这些约束与 `tools/probe-hyperos.ps1` 里已修复的三处 bug 一一对应
> （见 [docs/01](01-可行性分析.md) 第 7 节的踩坑记录）。

## 4. 布局引擎（LayoutEngine）

纯函数，输入屏幕可用区 + 预设 + 槽位数，输出每个槽位的 `Bounds`。

约束与不变量（**单元测试覆盖**）：

1. 所有 `Bounds` 两两不重叠（可共享一条边）。
2. 所有 `Bounds` 都落在可用区内（含状态栏/导航栏内缩）。
3. 主位（slot 0）面积 ≥ 任意其它槽位。
4. 槽位数少于预设格数时，空缺格并入主位（不留空洞）。
5. 槽位数多于预设格数时，多出的槽位**环绕主位**等分剩余区域，不越界。

预设示意（竖屏 **1220×2656**，本机实测真实分辨率；可用区去掉状态栏/手势条，间距 8px）：

| 预设 | 布局 |
| --- | --- |
| `STACK_2` | 上下各 50% |
| `SIDE_2` | 左右各 50% |
| `MAIN_SIDE` | 上方 62% 主位 + 下方 38% 横向均分（视频 + 挂机位） |
| `GRID_4` | 2×2 均分 |
| `MAIN_3MINI` | 左侧 66% 主位 + 右侧 34% 竖排 3 个迷你位 |

`MAIN_3MINI` 是"1 个游戏主位 + 3 个挂机/视频位"的推荐预设，也是发热和体验的平衡点。

## 5. 一步式 Dock（DockView）

| 手势 | 行为 | 实现 |
| --- | --- | --- |
| 单击图标 | 该 App 换到主位（其余自动重排） | `focusTask` + `LayoutEngine` 重排 |
| 长按图标 | 弹出菜单：全屏 / 关闭 / 保活 / 移出场景 | 自绘 popup（不新开窗口，避免焦点问题） |
| 拖拽图标到 Dock 外 | 交换主位 / 换槽位 | 落点判定 → 更新 `Scene.slots` 顺序 |
| 双击 Dock 空白 | 循环切换布局预设 | 预设列表轮转 |
| 长按 Dock 空白 | 拖动整条 Dock 到屏幕另一侧 | `WindowManager.updateViewLayout` |
| 滑出屏幕边缘 | 收起为细条 | 动画 + `FLAG_NOT_FOCUSABLE` 全程不变 |

**Dock 窗口参数（关键，防止游戏暂停）**

```kotlin
WindowManager.LayoutParams(
    WRAP_CONTENT, MATCH_PARENT,
    TYPE_APPLICATION_OVERLAY,
    FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_NO_LIMITS or FLAG_LAYOUT_IN_SCREEN,
    PixelFormat.TRANSLUCENT
)
```

`FLAG_NOT_FOCUSABLE` 是硬要求：Dock 一旦可获焦，点一下就会把焦点从游戏抢走。

## 6. 状态机

```
IDLE ──开工──► PROBING ──(档位确定)──► LAUNCHING ──(全部窗口就位)──► RUNNING
                  │                        │                            │
                  └──(无可用档位)──► DEGRADED ◄──(用户手动降级)──────────┘
                                            │
RUNNING ──切换主位/换布局──► REARRANGING ──(重排完成)──► RUNNING
RUNNING ──收工──► STOPPING ──(撤销保活/窗口回全屏)──► IDLE
```

任一阶段异常都要落到 `DEGRADED` 并**给出人话原因**（哪条命令失败、哪一步回退），
不允许出现"点了没反应"。这条是最容易被忽视、但决定项目能不能用的地方。
