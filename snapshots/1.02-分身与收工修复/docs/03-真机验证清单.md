## 阶段 0 · PC 端探测（不装 App，只读）

```powershell
# 手机开 USB 调试并连接，或先 adb connect <ip:port>
.\tools\probe-hyperos.ps1 -Serial <可选：设备序列号>
```

| 编号 | 看什么 | 通过标准 | 不通过 |
| --- | --- | --- | --- |
| P0 | `am` 命令面：是否支持 `--windowingMode`、`--bounds`、`am task resize/focus` | 打印出这些选项 | 记录哪些没有，App 会自动降级 |
| P1 | `settings get global enable_freeform_support` | `1` | 实测本机为 `0` 但 `FEATURE_FREEFORM_WINDOW_MANAGEMENT=True` → **可用，无需改设置/重启**（见下） |
| P2 | 用系统设置 App 试拉一个自由窗口 | `dumpsys activity activities` 出现 `mode=freeform` / `windowingMode=5` | 见"P2 失败" |
| P3 | `am task resize` 把该窗口改成 540×1200 | 窗口真的变小 | 见"P3 失败" |
| P4 | `am task focus <taskId>` | 该窗口置顶 | 退到 `--activity-reorder-to-front` |
| P5 | 再拉第二个 App 成自由窗口 | 两个自由窗口**同时存在** | ROM 只允许 1 个 → 方案降级为"1 小窗 + 快速切换" |
| P6 | 两个窗口都在时，观察第一个的动画/计时 | 仍在动（multi-resume 生效） | 该 App 会自我暂停 → 换 App 或接受降级 |
| P7 | 保活命令 | `cmd deviceidle whitelist +<pkg>` 等有输出、无报错 | 逐条记录哪条不可用 |
| P8 | 可选：`hyper_freeform_x` 广播 | `Broadcast completed` | 无该模块就跳过，`SKIP` 不是错误 |
| P9 | 小米私有小窗服务 `mi_freeform` | `service list` 里能找到它 | 有 → A+ 档可用；AIDL 需按 ROM 版本适配（参考 Mi-FreeForm） |
| P10 | 虚拟屏通路 + 调用身份 | `service list` 含 `display`，`id` 显示 `uid=2000(shell)` | **必须 shell 身份**：root 身份创建虚拟屏会抛 `packageName must match the calling uid` |
| P11 | `am` 的 display 能力面 | `--display` 与 `display move-stack` 都在 | 都缺 → "一键切前台"要退到"重新 launch"，代价是 App 重新加载 |
| P12 | 当前 display 列表 | 记录显示设备数量作为基线 | 虚拟屏创建后该数字应增加 |
| P13 | 虚拟屏上的 App 保持 `RESUMED` | `dumpsys activity activities` 中该任务 state 为 `RESUMED` | **App 内实测（M2）**；失败则"多个同时运行"不成立 |
| P14 | 任务跨屏搬迁（一键切前台核心） | `am display move-stack` 或 binder `moveTaskToDisplay` 生效 | App 内实测（M3）；失败则退到重新 launch |
| P15 | 锁屏/息屏后虚拟屏上的 App 继续运行 | 锁屏 10 分钟后解锁，App 仍在跑 | 挂机场景的成败点 |
| P16 | 虚拟屏上 App 的音频继续 | 副槽播放视频，声音正常 | 看视频场景的成败点 |
| P17 | 目标 App 是否自带前台服务 | `dumpsys activity services <pkg>` 含 `isForeground=true` | 有 → 轻量保活就够；无 → 需要虚拟屏 |
| P18 | **虚拟屏实验**（`-VirtualDisplayTest`） | 建屏后把 App 放上去，任务 `state=RESUMED` | **这是 M2 的 go/no-go**：`RESUMED` → 架构成立；`STOPPED` → 需求退到微窗或 C 档 |

### 阶段 0.5 · 虚拟屏 go/no-go（可选但强烈建议）

```powershell
.\tools\probe-hyperos.ps1 -VirtualDisplayTest
```

它会：记录 display 基线 → 造一块虚拟屏 → 把目标 App 放上去 → 读它的 `state` → **自动清理设置**。
脚本不会替你锁屏；锁屏存活（P13）请手动做：把 App 放到虚拟屏上 → 锁屏 10 分钟 → 解锁看它是否还在跑。

### P2 失败怎么办

1. 确认 P1 的判定没被"开关=0"误导（本机 `enable_freeform_support=0` 但自由窗口可用）。
2. 换成给系统设置 App 本身（它必然 `resizeableActivity=true`）再试，排除是目标 App 的声明问题。
3. 仍然失败 → 走档位 B/C：不追求自建自由窗口，改用 HyperOS 自带小窗 + Shizuku 保活 + 一键切换。
   这条路能覆盖"挂机 + 看视频"的主诉求，只是**不能自定义栅格**。

### P3 失败怎么办

窗口能开、不能改大小，先分两种可能：

1. **命令写错了**（最常见）：`am task resize` 的参数必须是 **4 个分开的数字**
   （`am task resize 91 0 0 540 1200`），写成逗号串会抛
   `NumberFormatException: For input string: "0,0,540,1200"`，
   看起来像"命令被拒"，实际是参数形状错误——**这正是本项目上一次误判的根因**。
2. **任务不在 freeform 栈里**（或被 ROM 标为不可 resize）：
   改用"启动时就带目标尺寸"的策略链（App 内 `setLaunchBounds`），而不是事后 resize。

### P18.3 的结论（D 档的关键约束）

> `overlay_display_devices` 造出来的屏是**系统持有**的，shell(uid=2000) **无权往它启动 Activity**，
> 所以它**不能当"后台槽"容器**。
> **D 档必须由 App 自己创建 VirtualDisplay**（`ownerUid=2000`，走 `DisplayManager` binder / `VirtualDisplayConfig`）。

### 最终结论

> **档位 A（系统自由窗口真同屏平铺）在本机实测成立**——窗口起得来、**两个能同时并存**、尺寸改得动（连 127dp 宽都照单全收）、任务前置得了。
> 下一步：编译 APK 装到手机，直接试 `MAIN_3MINI` 预设（阶段 1–3）。
> **档位 D**（虚拟屏后台槽、App 不占屏）保留为**可选增强**，前置条件是 M2-2「自建 VirtualDisplay」PoC。

### 阶段 0.8 · 平铺尺寸与 dump 格式实测（2026-10，第二轮）

> 这一轮解决的是"档位 A 真能在这个屏幕上铺开吗"这个最后的疑问。结论：**能，没有任何尺寸下限拦路。**

**1. 屏幕比想象的窄，但平铺不受限**

这台机器是**折叠机（有外屏）**，主屏只有 375dp 宽：

| displayId | 类型 | 像素 | dp | 备注 |
| --- | --- | --- | --- | --- |
| 0 | 内屏（主屏） | 1220×2656 @520dpi | **375×817 dp** | 应用跑在这里；`DisplayFrames` 顶部挖孔 inset = 150px（约 46dp） |
| 1 | 外屏 | 904×572 | 321×203 dp | `com.xiaomi.subscreencenter`（合盖时用） |

`dumpsys` 里确实写着 `mMinSizeOfResizeableTaskDp=200`，一度让人担心"两列平铺（约 186dp）会被系统夹到 200dp"。
实测**不会**：`am task resize 125 <L> <T> <R> <B>` 连续 5 组尺寸**全部被逐像素原样采纳**：

| 请求 | 实际结果 | 判定 |
| --- | --- | --- |
| 412×800 px = **127×246 dp** | `Rect(0,200-412,1000)` | ✓ 原样采纳（低于 200dp 也不拦） |
| 606×1250 px = **186×385 dp** | `Rect(0,150-606,1400)` | ✓ 原样采纳（两列平铺的目标尺寸） |
| 806×1250 px = 248×385 dp | `Rect(0,150-806,1400)` | ✓ |
| 1220×2441 px = **375×751 dp**（整屏） | `Rect(0,150-1220,2591)` | ✓ |
| 1220×348 px = 375×**107** dp | `Rect(0,150-1220,498)` | ✓ 原样采纳（低于 200dp 高也不拦） |

> 那条 200dp 只约束**用户拖窗口手柄**这一路径，`am task resize` / `IActivityTaskManager.resizeTask` 走的是另一条路。
> 顺带确认：自由窗口**默认尺寸不是全屏**——计算器起窗时是 `609×1220px = 187×375dp` 居中偏下（`Rect(306,760-915,1980)`），
> 所以"先启动再 resize"这条链路里，**resize 是必需步骤，不是可选优化**。

**2. Android 17 的 dump 长这样（解析器的依据）**

```
  * Task{618a9ed #91 type=standard A=10332:com.tencent.nrc U=0 visible=true visibleRequested=true mode=freeform translucent=false sz=1}
    mBounds=Rect(44, 329 - 584, 1529)
    mLastPausedActivity: ActivityRecord{70389491 u0 com.tencent.nrc/com.tencent.gcloud.msdk.core.policy.MSDKPolicyV3Activity t-1 f}}
    mLastNonFullscreenBounds=Rect(826, 462 - 1831, 842)
    topResumedActivity=ActivityRecord{29122565 u0 com.tencent.nrc/com.epicgames.ue4.GameActivity t91}
    ...
    rootOfTask=true task=Task{618a9ed #91 type=standard A=10332:com.tencent.nrc}
```

三个必须记住的坑（都已写进 `TaskInspector` 与单测）：

1. **包名和窗口模式都在任务头那一行**（`A=10332:com.tencent.nrc`、`mode=freeform`），不在块内部。
   桌面这类任务是 `type=home I=com.miui.home/.launcher.Launcher`——**只有 `I=` 没有 `A=`**，所以解析器要拿 `I=包名/` 兜底。
2. **`mLastPausedActivity` 出现在 `topResumedActivity` 前面**。谁要是"取块里第一个 ActivityRecord"，拿到的是已经暂停的
   `MSDKPolicyV3Activity`，而不是正在显示的游戏本体 `com.epicgames.ue4.GameActivity`。
3. **块内部会出现"引用行"**，例如 `rootOfTask=true task=Task{...}`、`(freeform) Task{...}`。
   必须要求任务头出现在行首，否则引用行会把任务块就地截断，后面的 `mBounds`/`topResumedActivity` 全部读不到
   → 表现为"任务存在但坐标是空的" → 被误判成 resize 失败。

**3. 解析器已加回归保护**

- `app/src/test/java/com/onestep/workbench/system/TaskInspectorTest.kt`：用**上面这段逐字真机 dump** 做 JVM 单测（8 个用例），编译时随 `testDebugUnitTest` 一起跑。
- `tools/verify-taskinspector.py`：同一套用例的 Python 等价移植，开发机没有 JDK 时也能先跑（**21 项检查全绿**）。

## 阶段 1 · 安装与授权

1. `adb install -r app\build\outputs\apk\debug\app-debug.apk`
2. 确认 Shizuku 已通过 adb / 无线调试启动，并给本应用授权。
3. 打开 App → 授权页应显示 **Shizuku: 已连接（uid=2000）**。
4. 授予「显示在其他应用上层」「通知」权限。
5. 点「一键自检」→ **逐条对照阶段 0 的结论**，两边必须一致。
   不一致 = 有 bug，不要继续。

---

## 阶段 2 · 最小可用验证（1 个 App）

1. 场景里只放 1 个 App（建议先用计算器/设置这类轻量 App），预设 `STACK_2`。
2. 点「开工」→ 该 App 应变成**非全屏的自由窗口**。
3. 侧边 Dock 出现；点图标 → 窗口回主位；双击空白 → 布局循环。
4. **焦点测试（最重要）**：打开一个全屏游戏或视频，点一下 Dock 上的图标，
   游戏/视频**不应该暂停**。若暂停了，说明 Dock 抢了焦点，检查 `FLAG_NOT_FOCUSABLE`。

---

## 阶段 3 · 双 App 同屏（核心假设）

1. 场景放 2 个 App：一个视频类 + 一个轻量 App，预设 `SIDE_2`。
2. 开工后两个窗口应左右并排、**都可见**。
3. 在 A 窗口里操作，B 窗口的视频应**继续播放**。
4. 点 Dock 把 B 换到主位 → A 应缩到侧位且**不重新加载**（不出现启动图/白屏）。

第 4 步是"一键切换"的核心验收点：**不重新加载**才说明窗口一直活着。

---

## 阶段 4 · 挂机保活

1. 场景里加一个真实挂机游戏，开启「挂机保活」。
2. 自检页确认：`deviceidle whitelist` 含该包、`standby-bucket=active`、`RUN_ANY_IN_BACKGROUND=allow`。
3. 锁屏 10 分钟 → 解锁：游戏应还在、未掉线（网络心跳类游戏）。
4. 「收工」后复查：上述三项**已撤销**。

---

## 阶段 5 · 压力与边界

| 项 | 观察 |
| --- | --- |
| 3 个窗口（`MAIN_3MINI`） | 是否有明显掉帧、机身温度、降频 |
| 4 个窗口（`GRID_4`） | 大概率不可用，记录阈值（这是给用户的"上限"依据） |
| 横竖屏切换 | 布局是否按新尺寸重算 |
| 来电 / 闹钟 / 弹窗 | 唤醒后工作台是否还在 |
| 重启手机 | Freeform 开关是否被重置（R3），Dock 是否能自恢复 |
