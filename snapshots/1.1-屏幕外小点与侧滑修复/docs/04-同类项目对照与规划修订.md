## 二、被修正的三条假设

### 假设 1（错）：多窗口必须把**系统窗口**铺在屏幕上

**原判断**：用 `windowingMode=5` 把每个 App 变成系统自由窗口，再用 `am task resize` 铺栅格。

**修正**：OneStep4 明确写着"**项目不依赖 Android 自由窗口模式**"，它用
`VirtualDisplay + SurfaceView` 把应用的画面渲染进**自己 App 的 UI 里**，触摸、输入法、焦点再转发给对应虚拟屏。
这样做的好处是决定性的：

- 不受 ROM 自由窗口策略限制（不怕"只允许一个小窗"）；
- 布局、动画、层级、切换全部由自己说了算——**"原子工作台"的实时卡片本质上就是这个**；
- 每个虚拟屏都是"开着"的显示设备，上面的 Activity 一直是 `RESUMED`，天然满足"同时运行"。

**代价**：工程量明显更大（要处理画面镜像、触摸注入、输入法、焦点），且需要虚拟屏权限。

**结论**：把"虚拟屏方案"提升为**首选档位**，系统自由窗口降级为"轻量档位"。

### 假设 2（错）：不做"同一个 App 多开"

**原判断**：同一 App 多开需要分身/多用户沙箱，与本方案是两条路，明确排除。

**修正**：虚拟屏天然就是隔离环境，Ynkcc/VirtualDisplay 与 Ruto-GLM 都用它做"应用分身/多开"。
也就是说——**加一个虚拟屏 = 加一个实例**，不需要分身框架。用户"多个游戏同时挂机"如果指同一个游戏开多号，
这条路直接覆盖。

**结论**：把"多开"从"不做"改成"档位 D 的副产品"。

### 假设 3（不完整）：Shizuku 层只需要"跑 shell 命令"

**原判断**：用 `Shizuku.newProcess` 跑 `am` / `settings` / `cmd`，靠解析输出来判断成败。

**修正**：Mi-FreeForm 走的是 **binder**：`ServiceManager.getService("mi_freeform")` →
`IMiFreeformUIService.startAppInFreeform(pkg, activity, userId, pendingIntent, width, height, densityDpi, ...)`。
拿到的是**小米官方小窗服务**，可以直接指定尺寸和 DPI，比 `am start --windowingMode 5` 精确得多，
而且不会产出"没有上下杆子的裸 AOSP 自由窗口"。

**结论**：
1. shell 命令保留为**兜底**（它的优点是 ROM 无关、输出可判定）；
2. 增加 **binder 直调**作为主路径，分两条：`mi_freeform`（小米私有）与 `IActivityTaskManager`（AOSP 通用）；
3. 需要 `HiddenApiBypass`（LSPosed 的隐藏 API 绕过库）才能拿到 `ServiceManager`。

## 三、修订后的档位

| 档位 | 机制 | 参考实现 | 适配场景 | 前提 |
| --- | --- | --- | --- | --- |
| **D · 虚拟屏工作台**（首选） | shell 创建 public `VirtualDisplay`；App 把自己 `SurfaceView` 的 Surface 交给 shell 侧 `setSurface` 做实时画面；触摸/按键按 displayId 注入 | Ynkcc/VirtualDisplay、Ruto-GLM、OneStep4 | **多游戏挂机 + 看视频 + 同一 App 多开** | Shizuku 以 **shell 身份**（非 root）启动；`CREATE_VIRTUAL_DISPLAY` |
| **A · 系统自由窗口平铺** | `windowingMode=5` + `am task resize` | Extendroid、本方案第一版 | 轻量同屏、2–3 个窗口 | ROM 打开 Freeform（P1–P3） |
| **A+ · 小米原生小窗服务** | binder 调 `mi_freeform` 的 `startAppInFreeform` | Mi-FreeForm | 想要官方小窗手感与精确尺寸 | 该 ROM 上存在 `mi_freeform` 服务（P9） |
| **B · 厂商小窗 + 保活** | HyperOS 自带小窗/迷你小窗 + 保活 | — | 单挂机位 | HyperOS 自带 |
| **C · 快速切换** | 保活 + 前置 | — | 兜底 | 任何有 Shizuku 的设备 |

**决策树**：`D` 可用 → 用 D（最贴合"多开挂机 + 看视频"）；
`D` 不可用但 A/A+ 可用 → 用平铺；都不行 → B/C。

## 四、新增探测项

| 编号 | 内容 | 命令 | 判读 |
| --- | --- | --- | --- |
| **P9** | 小米原生小窗服务是否存在 | `service list` 里找 `mi_freeform`；`dumpsys mi_freeform` | 存在 → A+ 档可用（但 AIDL 需按 ROM 版本适配） |
| **P10** | 虚拟屏通路 + 调用身份 | `service list` 含 `display`；`id` 确认 `uid=2000(shell)` | **必须是 shell 身份**：部分 ROM 会校验 packageName 与调用者 uid，root 身份会抛 `SecurityException` |
| **P11** | 虚拟屏创建实测（阶段 2 再做） | 在 App 内创建 1 个 1080×2400 虚拟屏并 `setSurface` 到预览 View | 能出画面 = D 档成立 |

> P10 的细节来自 [Ynkcc/VirtualDisplay 的 README](https://github.com/Ynkcc/VirtualDisplay)：
> `packageName must match the calling uid` 这条报错的解法就是"以 adb/shell 身份激活 Shizuku，而非 root"。

## 五、修订后的里程碑

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| **M1**（已有） | 能力自检 + 系统自由窗口平铺 + 一步式 Dock + 挂机保活 | 双窗口同屏、切换不重新加载（docs/03 阶段 2–3） |

| **M3**（新增） | 工作台外壳：主位 + N 个迷你卡的实时预览网格，点击换主位 | "原子工作台"观感成型；切换不重启应用 |
| **M4**（新增） | 多实例：同一 App 在两个虚拟屏各自运行 | 两个实例互不干扰、都在跑 |
| **M5** | 保活与功耗：息屏保持、温控提示、按需释放虚拟屏 | 长时间挂机不掉线 |
